# Per-Application Implementation Architecture — Meridian Health Network on Azure

`docs/azure-implementation.md` maps every logical component to an Azure service. This document goes one level deeper: for each application, it answers the questions a design review actually asks — what compute it runs on and how many instances, exactly how it reaches its database, whether it's public or private and who can reach it, and how it scales and survives a failure. Four applications are covered: CareLink PM (the replatformed vendor core), MeridianConnect Portal (the refactored owned application), Telehealth (the repurchased third-party service), and LinkEngine (the refactored integration layer).

## 1. CareLink PM (Core PM Service)

**Migration strategy:** Replatform (ADR-001). **Compute:** Citrix Virtual Apps and Desktops on Azure VMs (ADR-005). **Database:** Azure SQL Managed Instance, Business Critical tier, zone-redundant (ADR-006) — this is the direct answer to "which Azure database service and why": Managed Instance was chosen over Azure SQL Database specifically because a mature vendor product like CareLink PM is likely to depend on SQL Server Agent jobs, cross-database queries, or linked servers that only Managed Instance supports at near-full compatibility.

**Hosting architecture.** CareLink PM's compute is not a simple "VMs behind a load balancer" — Citrix has its own control plane, and the implementation decision from ADR-005 was to keep using it rather than replace it. Meridian's existing Citrix Cloud subscription remains the control plane (session brokering, published app catalog); only the infrastructure Citrix actually runs sessions on moves to Azure. Concretely:

- **Cloud Connectors** — four Azure VMs (one per Availability Zone plus a spare), in their own dedicated `snet-cloud-connectors` subnet (10.20.6.0/24) separate from the VDA session hosts, whose only job is to bridge Citrix Cloud's SaaS control plane to the Azure-hosted session hosts. They make outbound-only connections to Citrix Cloud; nothing inbound from the internet ever reaches them directly. See ADR-005's Proposed Configuration for why this is four, not the commonly-cited minimum of two.
- **VDA session hosts** — the actual CareLink PM delivery machines, organized into a Machine Catalog spread across three Availability Zones, Dsv5-series (`Standard_D8s_v5`), Windows Server 2022. The catalog autoscales between an off-peak floor of roughly 6–9 VMs and a day-one peak of roughly 45 VMs (today's ~1,800 concurrent sessions), sized up to a 36-month target ceiling of roughly 125 VMs (5,000 concurrent sessions) — see ADR-005's Proposed Configuration for the concurrency data and sizing assumptions behind these numbers. This is where clinicians' sessions actually run.
- **Database connectivity** — each VDA connects to Azure SQL Managed Instance over a private endpoint inside the data spoke VNet, TDS port 1433, TLS-encrypted. The SQL login is retrieved from Azure Key Vault at boot via the VM's managed identity — never embedded in a config file or image.

**Public or private, and how staff reach it.** Nothing in the application or data spoke has a public IP. A provider's device reaches Citrix Cloud's Gateway Service over the public internet (HDX protocol over TLS 443) — that's the only public-facing hop in the whole path. Citrix Cloud brokers the session and connects inward to a Cloud Connector, which routes to an available VDA. The connection into Azure is always broker-initiated from the Cloud Connector outward; a clinic never opens an inbound port to Meridian's network, which is what makes this compatible with the Zero Trust posture from ADR-002 without a VPN.

**Scaling and HA.** Citrix's own autoscale (not Azure VM Scale Sets) power-manages the VDA pool: additional session hosts spin up per zone on a schedule matched to clinic hours, and scale back down overnight. High availability comes from spreading the Machine Catalog across three zones — losing one zone removes roughly a third of capacity, not all of it — plus redundant Cloud Connectors so the control-plane bridge itself isn't a single point of failure.

## 2. MeridianConnect Portal

**Migration strategy:** Refactor (ADR-002) — this is Meridian-owned code, so unlike CareLink PM it can actually be rebuilt for the target platform. **Compute:** Azure App Service, Premium v3, Linux (ADR-010) — chosen over AKS/Container Apps because the Portal is one refactored web application with a conventional scaling profile, not a services mesh; App Service Premium v3 is also the tier that gives it both zone redundancy and the regional VNet integration it needs to reach SQL MI privately. **Database:** the same Azure SQL Managed Instance, a separate database within it.

**Hosting architecture.** The App Service plan is zone-redundant (Premium v3 spreads instances across Availability Zones automatically) and regionally VNet-integrated into the application spoke, which is what lets it reach SQL Managed Instance over a private endpoint instead of a public connection string. Azure Front Door Premium sits in front of it as the actual public entry point, running a WAF policy against the OWASP core rule set, and reaching App Service over Private Link rather than the public internet — App Service's access restrictions are configured to reject everything except traffic arriving through that Private Link path. The database connection string itself is never stored in App Service configuration directly; it's pulled from Key Vault via a Key Vault reference, resolved using the App Service's managed identity.

**Public or private, and how patients and staff reach it.** This one genuinely is public-facing, because patients need to reach it from their own devices with no VPN or corporate network — but "public-facing" means Front Door is public, not that App Service is. Two distinct identity providers sit behind the login screen: patients authenticate against **Microsoft Entra External ID** (ADR-009), a consumer identity product kept deliberately separate from the workforce directory; providers and staff authenticate against the same **Microsoft Entra ID** tenant (with Conditional Access and MFA) used everywhere else in this design. The portal itself decides which federation to invoke based on which login path the user takes.

**Scaling and HA.** Autoscale rules target 3 to 10 instances (P1v3) based on CPU utilization and HTTP request queue length, covering both steady traffic and spikes (open-enrollment periods, a weather event driving a surge in appointment rescheduling). The floor of 3 is an availability requirement — one instance per Availability Zone — not a load minimum; see ADR-010's Proposed Configuration for how the ceiling was estimated from the patient population and appointment data actually captured in this case study, since (unlike CareLink PM's Citrix sessions) no direct portal concurrency figure exists yet. Zone redundancy handles a single zone failure; Front Door's health probes and the paired-region warm standby (ADR-004) handle a full regional failure.

## 3. Telehealth Service

**Migration strategy:** Repurchase (ADR-002) — a deliberate non-build. This section exists mainly to be explicit about what Meridian does *not* host, since that's as much a design decision as anything built.

**Hosting architecture.** There isn't one, on Meridian's side — that's the point of Repurchase. The vendor's video/call platform and scheduling API run entirely on the vendor's own infrastructure. MeridianConnect Portal launches a session using the vendor's SDK or a deep link; from that point, video and audio media flow **directly between the patient's or provider's device and the vendor's infrastructure**, never proxied through Meridian's VNet or Front Door. That's a deliberate choice, not an oversight: real-time media is latency- and bandwidth-sensitive in a way that makes routing it through an extra hop actively harmful, and Meridian has no compliance reason to intercept it — the vendor is contractually the business associate responsible for that traffic under the BAA.

**What does touch Meridian's Azure environment:** SSO federation (the vendor is configured as a SAML/OIDC relying party against Meridian's Entra ID, so nobody needs a separate telehealth password) and a narrow appointment-sync integration — inbound webhooks for status changes and outbound API calls for scheduling — brokered through Azure API Management like any other external partner integration.

**Public or private:** APIM's webhook endpoint is necessarily public (the vendor calls it from outside Meridian's network), secured with signature validation and an API key held in Key Vault, exactly like the LabCorp/Quest integration path in Section 4.

**Scaling and HA:** not Meridian's concern for the vendor side — that's covered by the vendor's own SLA, which is exactly why Repurchase was the right call for a component with no clinical-record ownership implications.

## 4. LinkEngine (Integration / Event Bus)

**Migration strategy:** Refactor (ADR-002) — already message-based on-prem, rebuilt on managed infrastructure. **Messaging platform:** Azure Service Bus, Premium tier (ADR-011) — this is the direct answer to "which messaging solution": chosen over Event Grid and Event Hubs specifically because per-patient session ordering and dead-lettering are native Service Bus features neither alternative provides out of the box. One topic per HL7 message category (lab results, imaging, e-prescribing, appointment events), each with dead-lettering and session support for ordered per-patient delivery. See ADR-011's Proposed Configuration for Messaging Unit sizing and a real gap in the current DR runbook around in-flight messages during a regional failover. (If what's meant by "SMS solution" is patient-facing text notifications — appointment reminders, for example — that's a distinct capability from LinkEngine's HL7 integration bus and would be built separately on Azure Communication Services; it isn't in scope for this component and hasn't been designed yet. Flag it if that's wanted as an explicit future item.)

**Processing compute.** This is the piece that was previously undecided: something has to actually run the subscriber code that reacts to a new Service Bus message. ADR-008 decides that's **Azure Functions, Elastic Premium EP1, one shared plan hosting four function apps (one per topic)** — deliberately *not* the Citrix VM tier that hosts CareLink PM, even though those VMs are already connected to the data spoke. The reasoning: Citrix's autoscaling is tuned for interactive clinical session load, which follows a completely different pattern from message-processing load (a burst of lab results overnight, a backlog after an outage). Keeping them separate means each scales on the signal that actually matters to it. Each function app keeps 1 Always Ready instance (avoiding cold-start on clinically time-sensitive categories like lab results and e-prescribing) and can burst to 20 during a backlog catch-up; concurrency is session-aware (up to 8 different patients processed in parallel per instance, one session/patient handled at a time to preserve order) — see ADR-008's Proposed Configuration for the full reasoning.

**A network gap this sizing pass found and fixed.** The Functions Premium plan needs its own subnet for regional VNet Integration — Azure doesn't allow two different App Service Plans to share one VNet-integration subnet, and `snet-appsvc` is already committed to the Portal's plan (ADR-010). `network-addressing.dot`/`.png` and `azure-implementation.md` §4.1 now include a new `snet-func-linkengine` (10.20.5.0/24) subnet for this, with SQL MI's NSG updated to allow inbound 1433 from it.

**Message flow.** An external system (LabCorp, Quest, a hospital PACS, Surescripts) posts to Azure API Management over mutual TLS; APIM validates the client certificate and applies rate limiting, then publishes to the relevant Service Bus topic using the patient ID as the session ID, so multiple messages for the same patient stay ordered. The matching Azure Function subscribes, writes the structured result into SQL Managed Instance over a private endpoint, archives the raw HL7 payload to immutable Blob Storage, then completes the message. If processing fails — most commonly a patient ID that doesn't match an existing record — the message is abandoned, retried up to a configured maximum, and then moved to the dead-letter queue with an alert to on-call, instead of silently disappearing the way the current on-prem LinkEngine does when CareLink PM is unreachable.

**Public or private:** only APIM's ingress is public-facing (secured with mutual TLS); Service Bus, the Function Apps, and the data-tier writes all stay inside the private VNet.

**Scaling and HA:** each Function App scales independently on its own topic's queue length; Service Bus Premium provides its own zone-redundant messaging infrastructure with a throughput SLA, independent of any single subscriber's health.

## 5. Summary — public exposure and identity per application

| Application | Public entry point | Identity | Private data path |
| --- | --- | --- | --- |
| CareLink PM | Citrix Cloud Gateway Service (SaaS, not Meridian's Azure) | Workforce Entra ID, via Citrix's own auth integration | Cloud Connector → VDA → SQL MI, all private |
| MeridianConnect Portal | Azure Front Door (WAF, Private Link to App Service) | Entra External ID (patients) + Entra ID (staff) | App Service → SQL MI, private endpoint |
| Telehealth | Vendor's own infrastructure (video/media); APIM webhook (sync only) | SSO federated from Entra ID | N/A — vendor-hosted |
| LinkEngine | Azure API Management (mutual TLS) | Client certificate / API key, not user identity | APIM → Service Bus → Functions → SQL MI / Blob, all private |

No application in this design has a database, storage account, or compute tier reachable directly from the public internet — every public entry point is a gateway (Citrix Cloud, Front Door, or APIM) that terminates public traffic and continues over a private path from there.
