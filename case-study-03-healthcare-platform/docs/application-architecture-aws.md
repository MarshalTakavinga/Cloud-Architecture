# Per-Application Implementation Architecture — Meridian Health Network on AWS

`docs/aws-implementation.md` maps every logical component to an AWS service. This document goes one level deeper, mirroring `application-architecture.md`'s structure for Azure: for each application, it answers the questions a design review actually asks — what compute it runs on and how many instances, exactly how it reaches its database, whether it's public or private and who can reach it, and how it scales and survives a failure. The same four applications are covered: CareLink PM (the replatformed vendor core), MeridianConnect Portal (the refactored owned application), Telehealth (the repurchased third-party service), and LinkEngine (the refactored integration layer).

## 1. CareLink PM (Core PM Service)

**Migration strategy:** Replatform (ADR-001, platform-neutral). **Compute:** Citrix Virtual Apps and Desktops on Amazon EC2 (ADR-012). **Database:** Amazon RDS Custom for SQL Server, Multi-AZ (ADR-013) — this is the direct answer to "which AWS database service and why": RDS Custom was chosen over standard Amazon RDS specifically because a mature vendor product like CareLink PM is likely to depend on OS-level integrations or linked-server configurations that only RDS Custom's OS/filesystem access supports, at the cost of some of standard RDS's fully hands-off automation.

**Hosting architecture.** CareLink PM's compute is not a simple "instances behind a load balancer" — Citrix has its own control plane, and the implementation decision from ADR-012 was to keep using it rather than replace it, exactly as ADR-005 decided for Azure. Meridian's existing Citrix Cloud subscription remains the control plane (session brokering, published app catalog); only the infrastructure Citrix actually runs sessions on moves to AWS. Concretely:

- **Cloud Connectors** — four EC2 instances (one per Availability Zone plus a spare), in their own dedicated `subnet-cloud-connectors-az1/az2/az3` (10.20.6.0/27, 10.20.6.32/27, 10.20.6.64/27 — one subnet per AZ, since an AWS subnet can't span zones the way an Azure VNet subnet can) separate from the VDA session hosts, whose only job is to bridge Citrix Cloud's SaaS control plane to the AWS-hosted session hosts. They make outbound-only connections to Citrix Cloud; nothing inbound from the internet ever reaches them directly. See ADR-012's Proposed Configuration for why this is four, not the commonly-cited minimum of two.
- **VDA session hosts** — the actual CareLink PM delivery machines, organized into a Machine Catalog spread across three Availability Zones, `m6i.2xlarge` instances, Windows Server 2022. The catalog autoscales between an off-peak floor of roughly 6-9 instances and a day-one peak of roughly 45 instances (today's ~1,800 concurrent sessions), sized up to a 36-month target ceiling of roughly 125 instances (5,000 concurrent sessions) — see ADR-012's Proposed Configuration for the concurrency data and sizing assumptions behind these numbers, reused unchanged from ADR-005 since the demand-side figures are platform-independent. This is where clinicians' sessions actually run.
- **Database connectivity** — each VDA connects to RDS Custom for SQL Server over a private VPC path, TDS port 1433, TLS-encrypted. The database login is retrieved from AWS Secrets Manager at boot via the instance's IAM role — never embedded in a config file or image.

**Public or private, and how staff reach it.** Nothing in the application or data VPC has a public IP. A provider's device reaches Citrix Cloud's Gateway Service over the public internet (HDX protocol over TLS 443) — that's the only public-facing hop in the whole path. Citrix Cloud brokers the session and connects inward to a Cloud Connector, which routes to an available VDA. The connection into AWS is always broker-initiated from the Cloud Connector outward; a clinic never opens an inbound port to Meridian's AWS network, which is what makes this compatible with the Zero Trust posture from ADR-002 without a VPN — identical to the Azure design.

**Scaling and HA.** Citrix's own autoscale (not EC2 Auto Scaling groups) power-manages the VDA pool: additional session hosts spin up per zone on a schedule matched to clinic hours, and scale back down overnight. High availability comes from spreading the Machine Catalog across three zones — losing one zone removes roughly a third of capacity, not all of it — plus redundant Cloud Connectors so the control-plane bridge itself isn't a single point of failure.

## 2. MeridianConnect Portal

**Migration strategy:** Refactor (ADR-002, platform-neutral) — this is Meridian-owned code, so unlike CareLink PM it can actually be rebuilt for the target platform. **Compute:** Amazon ECS on AWS Fargate (ADR-017) — chosen over EKS/App Runner because the Portal is one refactored web application with a conventional scaling profile, not a services mesh; Fargate is the option that gives it both VPC-private connectivity and zone-redundant HA without the operational surface of a Kubernetes cluster. **Database:** the same RDS Custom for SQL Server instance, a separate database within it.

**Hosting architecture.** The ECS service runs zone-redundant Fargate tasks (spread automatically across the three Availability Zones used elsewhere in this design) behind an internal Application Load Balancer, and is regionally VPC-integrated into the Application VPC, which is what lets it reach RDS Custom over a private path instead of a public connection string. Amazon CloudFront sits in front of it as the actual public entry point, with AWS WAF attached running a managed rule set, and reaching the internal ALB over a VPC origin rather than the public internet — the ALB's security group is configured to reject everything except traffic arriving through that path. The database connection string itself is never stored in the task definition directly; it's pulled from Secrets Manager at task startup, resolved using the ECS task's IAM role.

**Public or private, and how patients and staff reach it.** This one genuinely is public-facing, because patients need to reach it from their own devices with no VPN or corporate network — but "public-facing" means CloudFront is public, not that the ECS tasks are. Two distinct identity providers sit behind the login screen: patients authenticate against **Amazon Cognito User Pools** (ADR-016), a consumer identity product kept deliberately separate from the workforce directory; providers and staff authenticate against **AWS Directory Service for Microsoft AD** (with MFA enforced via IAM Identity Center) used everywhere else in this design. The Portal itself decides which federation to invoke based on which login path the user takes.

**Scaling and HA.** Autoscale rules target 3 to 10 Fargate tasks based on CPU utilization and ALB request count per target, covering both steady traffic and spikes (open-enrollment periods, a weather event driving a surge in appointment rescheduling). The floor of 3 is an availability requirement — one task per Availability Zone — not a load minimum; see ADR-017's Proposed Configuration for how the ceiling was estimated from the patient population and appointment data actually captured in this case study, reused unchanged from ADR-010 since no direct portal concurrency figure exists yet. Zone redundancy handles a single zone failure; CloudFront's health-check-driven origin failover and the paired-region warm standby (ADR-004) handle a full regional failure.

## 3. Telehealth Service

**Migration strategy:** Repurchase (ADR-002, platform-neutral) — a deliberate non-build. This section exists mainly to be explicit about what Meridian does *not* host, since that's as much a design decision as anything built — unchanged from the Azure design, because Repurchase means there's very little that's platform-specific to begin with.

**Hosting architecture.** There isn't one, on Meridian's side — that's the point of Repurchase. The vendor's video/call platform and scheduling API run entirely on the vendor's own infrastructure. MeridianConnect Portal launches a session using the vendor's SDK or a deep link; from that point, video and audio media flow **directly between the patient's or provider's device and the vendor's infrastructure**, never proxied through Meridian's VPC or CloudFront. That's a deliberate choice, not an oversight: real-time media is latency- and bandwidth-sensitive in a way that makes routing it through an extra hop actively harmful, and Meridian has no compliance reason to intercept it — the vendor is contractually the business associate responsible for that traffic under the BAA.

**What does touch Meridian's AWS environment:** SSO federation (the vendor is configured as a SAML/OIDC relying party against Meridian's Cognito/Directory Service setup, so nobody needs a separate telehealth password) and a narrow appointment-sync integration — inbound webhooks for status changes and outbound API calls for scheduling — brokered through Amazon API Gateway like any other external partner integration.

**Public or private:** API Gateway's webhook endpoint is necessarily public (the vendor calls it from outside Meridian's network), secured with signature validation and an API key held in Secrets Manager, exactly like the LabCorp/Quest integration path in Section 4.

**Scaling and HA:** not Meridian's concern for the vendor side — that's covered by the vendor's own SLA, which is exactly why Repurchase was the right call for a component with no clinical-record ownership implications, regardless of which cloud platform hosts everything else.

## 4. LinkEngine (Integration / Event Bus)

**Migration strategy:** Refactor (ADR-002, platform-neutral) — already message-based on-prem, rebuilt on managed infrastructure. **Messaging platform:** Amazon SNS FIFO + Amazon SQS FIFO (ADR-018) — this is the direct answer to "which messaging solution": chosen over Amazon MQ and Amazon MSK specifically because per-patient message-group ordering and dead-lettering are native SNS/SQS features that would require real infrastructure or engineering effort to replicate on the alternatives. One topic/queue pair per HL7 message category (lab results, imaging, e-prescribing, appointment events), each with dead-lettering and FIFO ordering for per-patient delivery. See ADR-018's Proposed Configuration for why SNS/SQS has no Messaging-Unit-equivalent capacity decision to make, and its explicit callout of a real gap: unlike Azure Service Bus, SNS/SQS have no native cross-region replication at all, not even topology.

**Processing compute.** This is the piece that was previously undecided: something has to actually run the subscriber code that reacts to a new message. ADR-015 decides that's **AWS Lambda, one function per queue, reserved concurrency 20, provisioned concurrency 1** — deliberately *not* the Citrix EC2 tier that hosts CareLink PM, even though those instances are already connected to the data VPC. The reasoning: Citrix's autoscaling is tuned for interactive clinical session load, which follows a completely different pattern from message-processing load (a burst of lab results overnight, a backlog after an outage). Keeping them separate means each scales on the signal that actually matters to it — the identical reasoning ADR-008 used for Azure Functions. Each Lambda function keeps 1 provisioned-concurrency instance warm (avoiding cold-start on clinically time-sensitive categories like lab results and e-prescribing) and can burst to a reserved concurrency ceiling of 20 during a backlog catch-up; batch size is kept at 1 to avoid breaking per-patient ordering within a single invocation — see ADR-015's Proposed Configuration for the full reasoning.

**A network difference this sizing pass surfaced, not a gap this time.** Unlike Azure, where the Functions Premium plan *had* to get its own subnet because Azure doesn't allow two App Service Plans to share one VNet-integration subnet, AWS Lambda functions can share a VPC subnet freely — there's no equivalent platform restriction. `subnet-lambda-linkengine-az1/az2/az3` (10.20.5.0/26, 10.20.5.64/26, 10.20.5.128/26 — three subnets, one per AZ, since an AWS subnet can't span zones the way an Azure VNet subnet can) is still used here, but for a different, honestly-stated reason: isolating IP-address consumption under burst concurrency from the other application-tier subnets, not because AWS requires it the way Azure does. Five functions share this subnet tier now, not four — the ingest-side Publish Function (below) alongside the four subscriber functions — for a combined ceiling of up to 90 concurrent executions (80 across the four subscribers, 10 for the Publish Function) at the reserved-concurrency limit. See ADR-015 for the subscriber-side explanation and ADR-018 for the Publish Function.

**Message flow.** An external system (LabCorp, Quest, a hospital PACS, Surescripts) posts to Amazon API Gateway over mutual TLS; API Gateway validates the client certificate and applies a usage-plan rate limit, then invokes the **Publish Function** (AWS Lambda, ADR-018) via a Lambda proxy integration. The Publish Function parses the raw HL7v2 message, extracts the patient ID, determines which of the four message categories it belongs to, and publishes to the matching SNS FIFO topic using that patient ID as the `MessageGroupId`, so multiple messages for the same patient stay ordered — this parsing step exists because API Gateway's mapping templates work against JSON/XML and can't reliably extract a field from raw pipe-delimited HL7v2 text, so a direct API Gateway-to-SNS service integration isn't viable here the way it might be for a JSON payload. The topic fans out to its SQS FIFO subscriber queue, and the matching Lambda function (triggered by the queue's event source mapping) writes the structured result into RDS Custom for SQL Server over a private VPC path, archives the raw HL7 payload to immutable S3 storage, then the message is deleted from the queue on success. If processing fails — most commonly a patient ID that doesn't match an existing record — the message becomes visible again, retried up to the configured `maxReceiveCount`, then moved to the dead-letter queue with a CloudWatch alarm to on-call, instead of silently disappearing the way the current on-prem LinkEngine does when CareLink PM is unreachable.

**Public or private:** only API Gateway's ingress is public-facing (secured with mutual TLS); SNS, SQS, the Lambda functions, and the data-tier writes all stay inside the private VPC.

**Scaling and HA:** each Lambda function scales independently on its own queue's backlog via the event source mapping; SNS/SQS are inherently multi-AZ, zone-redundant services with no tier decision required to get that redundancy, independent of any single subscriber's health.

## 5. Summary — public exposure and identity per application

| Application | Public entry point | Identity | Private data path |
| --- | --- | --- | --- |
| CareLink PM | Citrix Cloud Gateway Service (SaaS, not Meridian's AWS account) | Workforce AWS Directory Service, via Citrix's own auth integration | Cloud Connector → VDA → RDS Custom, all private |
| MeridianConnect Portal | Amazon CloudFront (WAF, VPC origin to internal ALB) | Cognito User Pools (patients) + Directory Service/IAM Identity Center (staff) | ECS Fargate → RDS Custom, private VPC path |
| Telehealth | Vendor's own infrastructure (video/media); API Gateway webhook (sync only) | SSO federated from Cognito/Directory Service | N/A — vendor-hosted |
| LinkEngine | Amazon API Gateway (mutual TLS) | Client certificate / API key, not user identity | API Gateway → SNS/SQS → Lambda → RDS Custom / S3, all private |

No application in this design has a database, storage bucket, or compute tier reachable directly from the public internet — every public entry point is a gateway (Citrix Cloud, CloudFront, or API Gateway) that terminates public traffic and continues over a private path from there. Identical posture to the Azure design; only the specific services differ.
