# Per-Application Implementation Architecture — Meridian Health Network on Private Cloud

`docs/private-cloud-implementation.md` maps every logical component to a private-cloud implementation. This document goes one level deeper, mirroring `application-architecture.md`/`application-architecture-aws.md`/`application-architecture-gcp.md`'s structure: for each application, it answers the questions a design review actually asks — what compute it runs on and how many instances, exactly how it reaches its database, whether it's public or private and who can reach it, and how it scales and survives a failure. The same four applications are covered: CareLink PM (the replatformed vendor core), MeridianConnect Portal (the refactored owned application), Telehealth (the repurchased third-party service), and LinkEngine (the refactored integration layer).

## 1. CareLink PM (Core PM Service)

**Migration strategy:** Replatform (ADR-001, platform-neutral). **Compute:** Citrix Virtual Apps and Desktops on VCF-managed vSphere VMs (ADR-027). **Database:** self-managed SQL Server 2022 Enterprise, Always On Availability Group (ADR-028) — this is the direct answer to "which database and why": there is no managed database tier in private cloud at all, so this is SQL Server operated by Meridian's own DBAs, deployed correctly across two physical facilities for the first time rather than two nodes in the same room.

**Hosting architecture.** CareLink PM's compute is not a simple "VMs behind a load balancer" — Citrix has its own control plane, and ADR-027's decision was to keep using it rather than switch to VMware's own native VDI product (Horizon), exactly as ADR-005/ADR-012/ADR-019 decided for Azure, AWS, and GCP, but here reached against a real, weighed alternative rather than an absent one. Meridian's existing Citrix Cloud subscription remains the control plane (session brokering, published app catalog); only the infrastructure Citrix actually runs sessions on moves onto VCF. Concretely:

- **Cloud Connectors** — four VMs (spread across the Production VI Workload Domain's ESXi hosts via anti-affinity, plus a spare), in the Application NSX segment, alongside the VDA session hosts, the Portal's Tanzu workload, and the API gateway runtime. They make outbound-only connections to Citrix Cloud; nothing inbound from the internet ever reaches them directly. See ADR-027's Proposed Configuration for why this is four, not the commonly-cited minimum of two.
- **VDA session hosts** — the actual CareLink PM delivery machines, organized into a Machine Catalog spread across ESXi hosts, 8 vCPU / 32 GB VMs, Windows Server 2022. The catalog scales between an off-peak floor and a day-one peak of roughly 45 VMs (today's ~1,800 concurrent sessions), sized up to a 36-month target ceiling of roughly 125 VMs (5,000 concurrent sessions) — see ADR-027's Proposed Configuration for the concurrency data, the sizing assumptions (reused unchanged from every sibling platform since the demand-side figures are platform-independent), and — unique to this track — the physical-host math those VM counts actually consume out of the Production VI Workload Domain's 8-to-20-host range (ADR-026). This is where clinicians' sessions actually run.
- **Database connectivity** — each VDA connects to the SQL Server Always On listener over the private NSX fabric (Data segment, ADR-029), TDS port 1433, TLS-encrypted. The database login is retrieved from Vault (Section 5 of `private-cloud-implementation.md`) at boot via the VM's attached service identity.

**Public or private, and how staff reach it.** Nothing in the Application or Data NSX segments has a public IP. A provider's device reaches Citrix Cloud's Gateway Service over the public internet (HDX protocol over TLS 443) — that's the only public-facing hop in the whole path, and it's unchanged by which platform sits behind Citrix Cloud. Citrix Cloud brokers the session and connects inward to a Cloud Connector, which routes to an available VDA. The connection into the private-cloud environment is always broker-initiated from the Cloud Connector outward; a clinic never opens an inbound port to Meridian's colocation facilities, which is what makes this compatible with the Zero Trust posture from ADR-002 without a VPN — identical to the Azure, AWS, and GCP designs.

**Scaling and HA.** Citrix's own autoscale (not vSphere-level scaling) power-manages the VDA pool: additional session hosts spin up on a schedule matched to clinic hours and scale back down overnight, within the ceiling of physical host capacity already provisioned (ADR-026) — a real constraint the hyperscaler tracks don't share, since a private-cloud "autoscale" can never exceed the physical hardware standing in the facility. High availability comes from vSphere DRS anti-affinity spreading the Machine Catalog across ESXi hosts within the Workload Domain — losing one host removes a bounded slice of capacity, not all of it — plus redundant Cloud Connectors so the control-plane bridge itself isn't a single point of failure.

## 2. MeridianConnect Portal

**Migration strategy:** Refactor (ADR-002, platform-neutral) — this is Meridian-owned code, so it can genuinely be rebuilt for the target platform. **Compute:** VMware Tanzu (ADR-032) — chosen over a fixed VM pool (elasticity mismatch) and full microservices (staffing); private cloud has no serverless container primitive of its own, so Tanzu is the closest available approximation, shared with LinkEngine's workload (ADR-030) rather than duplicated. **Database:** the same SQL Server Always On instance, a separate database within it.

**Hosting architecture.** The Portal runs as a set of containerized Deployments on the shared Tanzu cluster, reached over the Application NSX segment, which is what lets it reach SQL Server over the private fabric instead of a public connection string. The NSX Advanced Load Balancer (Avi) sits directly in front of the Tanzu Deployments as the internal load balancer. In front of *that*, a third-party SaaS CDN/WAF product is the actual public entry point — the mechanism ADR-032 names explicitly to close the gap that neither VCF, NSX, nor Tanzu includes any CDN or internet-facing WAF/DDoS-scrubbing capability of their own, unlike every hyperscaler sibling's bundled edge service (Cloud Armor+Cloud CDN, CloudFront+WAF, Front Door+WAF). The origin load balancer at each colocation facility accepts connections only from the CDN/WAF vendor's published IP ranges, so the facility's public IP is never reachable by anyone bypassing that layer. The database connection string is never stored in the container image or environment directly; it's pulled from Vault at startup using the Tanzu workload's attached service identity.

**Public or private, and how patients and staff reach it.** This one genuinely is public-facing, because patients need to reach it from their own devices with no VPN or corporate network — but "public-facing" means the CDN/WAF edge and the colocation facilities' load balancers are public, not that the Tanzu Deployments themselves are reachable directly. Two distinct identity providers sit behind the login screen: patients authenticate against the managed SaaS CIAM product (ADR-031); providers and staff authenticate directly against Meridian's existing on-prem Active Directory forest, reached without any hybrid-identity bridge — a genuine simplification unique to this track (ADR-031's Context). The Portal itself decides which federation to invoke based on which login path the user takes.

**Scaling and HA.** KEDA/Kubernetes autoscale rules target 3 to 10 Tanzu replicas based on concurrent request count, covering both steady traffic and spikes (open-enrollment periods, a weather event driving a surge in appointment rescheduling) — see ADR-032's Proposed Configuration for how the ceiling was estimated from the same patient population and appointment data used throughout this case study. Availability comes from the Tanzu cluster's own multi-node, anti-affinity-spread scheduling, the CDN/WAF layer's own edge redundancy, and the paired-facility warm standby (ADR-004) for a full primary-facility failure — with the DR-facility capacity caveat named in `private-cloud-implementation.md` §8: the Dallas Tanzu cluster is already provisioned at full target capacity, not scaled up on demand.

## 3. Telehealth Service

**Migration strategy:** Repurchase (ADR-002, platform-neutral) — a deliberate non-build. This section exists mainly to be explicit about what Meridian does *not* host, since that's as much a design decision as anything built — unchanged from the Azure, AWS, and GCP designs, because Repurchase means there's very little that's platform-specific to begin with, private cloud included.

**Hosting architecture.** There isn't one, on Meridian's side — that's the point of Repurchase. The vendor's video/call platform and scheduling API run entirely on the vendor's own infrastructure, regardless of what Meridian's own platform looks like underneath the Portal. MeridianConnect Portal launches a session using the vendor's SDK or a deep link; from that point, video and audio media flow **directly between the patient's or provider's device and the vendor's infrastructure**, never proxied through Meridian's colocation facilities or the CDN/WAF layer. That's a deliberate choice, not an oversight: real-time media is latency- and bandwidth-sensitive in a way that makes routing it through an extra hop actively harmful — doubly so here, since routing it through a private-cloud facility's own uplink instead of a hyperscaler's global network would add real, avoidable latency — and Meridian has no compliance reason to intercept it; the vendor is contractually the business associate responsible for that traffic under the BAA.

**What does touch Meridian's private-cloud environment:** SSO federation (the vendor is configured as a SAML/OIDC relying party against the CIAM product/Active Directory setup, so nobody needs a separate telehealth password) and a narrow appointment-sync integration — inbound webhooks for status changes and outbound API calls for scheduling — brokered through the API gateway like any other external partner integration.

**Public or private:** the API gateway's webhook endpoint is necessarily public (the vendor calls it from outside Meridian's network), secured with signature validation and an API key held in Vault, exactly like the LabCorp/Quest integration path in Section 4.

**Scaling and HA:** not Meridian's concern for the vendor side — that's covered by the vendor's own SLA, which is exactly why Repurchase was the right call for a component with no clinical-record ownership implications, regardless of which platform hosts everything else, private cloud included.

## 4. LinkEngine (Integration / Event Bus)

**Migration strategy:** Refactor (ADR-002, platform-neutral) — already message-based on-prem, rebuilt on managed infrastructure. **Messaging platform:** self-managed RabbitMQ, clustered with quorum queues (ADR-033) — this is the direct answer to "which messaging solution": chosen over self-managed Kafka and a commercial on-prem ESB product specifically because per-patient ordering keys and dead-lettering are native RabbitMQ features that map directly onto the same fan-out-plus-durable-queue pattern every sibling platform's messaging service provides. One topic per HL7 message category (lab results, imaging, e-prescribing, appointment events), each with a dedicated subscription carrying dead-lettering and ordering-key-based per-patient delivery.

**Processing compute.** This is the piece that was previously undecided: something has to actually run the subscriber code that reacts to a new message. ADR-030 decides that's **VMware Tanzu, one containerized Deployment per queue, autoscaled by KEDA against queue depth** — deliberately *not* the Citrix VM tier that hosts CareLink PM, even though those VMs are already connected to the Data segment. The reasoning: Citrix's own scaling is tuned for interactive clinical session load, which follows a completely different pattern from message-processing load. Keeping them separate means each scales on the signal that actually matters to it — the identical reasoning ADR-008/ADR-015/ADR-022 used on every sibling platform. Each Deployment keeps 1 replica warm (avoiding cold-start-equivalent latency on clinically time-sensitive categories like lab results and e-prescribing) and can burst to a ceiling of 20 replicas during a backlog catch-up; delivery is kept ordered per routing key to avoid breaking per-patient sequencing — see ADR-030's Proposed Configuration for the full reasoning.

**Network placement: isolated, for the same reason as every sibling platform.** LinkEngine's Tanzu-hosted workloads (the Publish Service and its four subscriber Deployments) run in their own dedicated Integration NSX segment (10.50.0.0/16 — see `private-cloud-implementation.md` §4.1), separate from the Application segment that hosts the API gateway runtime, the Portal's Tanzu Deployments, and Citrix — because this is the one compute tier in this design invoked by externally-triggered partner traffic (client certificate/API key via the API gateway), not a Meridian-authenticated user or staff member, a materially different trust boundary from what the Application segment hosts. Unlike the AWS design (which isolated Lambda for a genuine IP-capacity reason) and mirroring the GCP design's reasoning exactly, this isolation is a network/IAM blast-radius decision, not a capacity one — Tanzu pods have no per-execution IP-consumption behavior comparable to AWS Lambda's ENI model.

**Message flow.** An external system (LabCorp, Quest, a hospital PACS, Surescripts) posts to the API gateway over mutual TLS; the gateway validates the client certificate and applies a quota policy, then invokes the **Publish Service** (a Tanzu Deployment, ADR-033) via a backend route. The Publish Service parses the raw HL7v2 message, extracts the patient ID, determines which of the four message categories it belongs to, and publishes to the matching RabbitMQ exchange using that patient ID as the routing key, so multiple messages for the same patient stay ordered — this parsing step exists because the gateway's policy engine works against JSON/XML transforms and can't reliably extract a field from raw pipe-delimited HL7v2 text, the identical real constraint every sibling ADR names for its own API gateway product. The queue delivers the message to its Tanzu subscriber Deployment, which writes the structured result into SQL Server over the private NSX fabric, archives the raw HL7 payload to the object-storage layer, then acknowledges the message on success. If processing fails — most commonly a patient ID that doesn't match an existing record — the message is redelivered, retried up to the configured delivery limit, then moved to the dead-letter exchange with an alert to on-call, instead of silently disappearing the way the current on-prem LinkEngine does when CareLink PM is unreachable.

**Public or private:** only the API gateway's ingress is public-facing (secured with mutual TLS); RabbitMQ, the Tanzu Deployments, and the data-tier writes all stay inside the private NSX fabric.

**Scaling and HA:** each Tanzu Deployment scales independently on its own queue's backlog via KEDA; the RabbitMQ cluster's own quorum-queue replication provides in-facility redundancy, independent of any single subscriber's health — with the caveat, named plainly in ADR-033, that none of this is a managed service, and the cluster's own health is now Meridian's operational responsibility in a way it isn't on any sibling platform.

## 5. Summary — public exposure and identity per application

| Application | Public entry point | Identity | Private data path |
| --- | --- | --- | --- |
| CareLink PM | Citrix Cloud Gateway Service (SaaS, not Meridian's private-cloud facilities) | Workforce Active Directory, via Citrix's own auth integration | Cloud Connector → VDA → SQL Server, all private |
| MeridianConnect Portal | Third-party CDN/WAF → colocation facility load balancer (NSX ALB, IP-allowlisted to the CDN/WAF vendor) | CIAM product (patients) + Active Directory (staff) | Tanzu → SQL Server, private NSX fabric |
| Telehealth | Vendor's own infrastructure (video/media); API gateway webhook (sync only) | SSO federated from the CIAM product/Active Directory | N/A — vendor-hosted |
| LinkEngine | API gateway (mutual TLS) | Client certificate / API key, not user identity | API gateway → Tanzu (Publish Service) → RabbitMQ → Tanzu (subscribers) → SQL Server / object storage, all private |

No application in this design has a database, storage bucket, or compute tier reachable directly from the public internet — every public entry point is a gateway (Citrix Cloud, the CDN/WAF-fronted load balancer, or the API gateway) that terminates public traffic and continues over the private NSX fabric from there. The same posture as the Azure, AWS, and GCP designs — but reaching it here required two deliberate, named external SaaS dependencies (the CIAM product and the CDN/WAF product) that the hyperscaler tracks got as bundled platform features, worth carrying into the Step 10 comparison as a genuine, not cosmetic, difference.
