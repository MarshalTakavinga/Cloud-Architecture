# GCP Implementation — Meridian Health Network

This document implements the vendor-neutral logical design on Google Cloud Platform. It is one of four parallel implementations (Azure, AWS, GCP, private cloud) that will be scored against each other in a weighted decision matrix — nothing here is the final platform choice. The point of building this thoroughly, rather than sketching it, is the same discipline `azure-implementation.md` and `aws-implementation.md` applied: a fair comparison requires each platform to actually be designed, not guessed at. Where GCP's answer is genuinely just "the same idea, a different product name," this document says so plainly; where GCP's own primitives (regional subnets, non-transitive peering, projects instead of accounts, Pub/Sub's combined topic/queue model) push toward a materially different design, this document says that too, rather than forcing a structural mirror of the Azure/AWS documents onto a platform that doesn't share their constraints.

This document covers the platform as a whole — service selection, networking, security, DR, IaC. For a deeper, per-application treatment of exactly how each of CareLink PM, MeridianConnect Portal, Telehealth, and LinkEngine is hosted, connects to its data, is reached by users, and scales — see [`application-architecture-gcp.md`](application-architecture-gcp.md).

Where a decision is genuinely platform-neutral (the migration strategy, the DR topology, the database engine family, the target architecture style), it is not re-litigated here — it's inherited from ADR-001 through ADR-004 and ADR-009 unchanged. This document and its ADRs (ADR-019 through ADR-025) only decide the GCP-specific *how*.

## 2. Compute — Hosting CareLink PM (see ADR-019)

CareLink PM is a Windows thick-client application currently published via Citrix Virtual Apps 7. The lowest-risk GCP implementation keeps that exact delivery model and moves only the infrastructure underneath it: Citrix Virtual Apps and Desktops supports Google Cloud as a resource location, so the instances Citrix publishes from simply move to Compute Engine, spread across zones instead of living in a single converted server room. Unlike the Azure and AWS comparisons, there is no real GCP-native alternative delivery mechanism to weigh this against — see ADR-019 for why that changes the shape of this ADR's rationale, and [`application-architecture-gcp.md` §1](application-architecture-gcp.md#1-carelink-pm-core-pm-service) for the full Cloud Connector / Machine Catalog hosting architecture.

## 3. Database — Cloud SQL for SQL Server (see ADR-020)

The logical design (ADR-003) already decided "managed relational, not NoSQL." The GCP-specific question is which managed relational offering — and unlike the Azure and AWS comparisons, this isn't a choice between two or three tiers of the same product family with different compatibility ceilings. GCP offers exactly one managed SQL Server tier (Cloud SQL for SQL Server) with no OS-access middle tier between it and fully self-managed Compute Engine. See ADR-020 for why Cloud SQL is chosen anyway, the real compatibility risk that decision accepts, and the one respect (native cross-region read replicas) in which it's actually stronger than AWS's RDS Custom. Both CareLink PM and MeridianConnect Portal use this same instance, as separate databases — see `application-architecture-gcp.md` for exactly how each application connects to it.

## 4. Networking and Landing Zone

- **Inspection VPC (hub)**: Cloud Next Generation Firewall (Cloud NGFW) for egress control and threat/intrusion filtering, attached to the Network Connectivity Center hub, plus the Cloud VPN / Cloud Interconnect attachment for any remaining on-prem/clinic connectivity during migration. Remote administrative access uses **Identity-Aware Proxy (IAP) TCP forwarding** rather than a bastion host — the direct GCP analog to AWS Systems Manager Session Manager: no inbound management port is ever opened, not even through a jump box.
- **Application VPC (spoke)**: the Apigee runtime, the Portal's Cloud Run service via Direct VPC egress, and Compute Engine Citrix instances — the platform's user-and-staff-facing compute, sharing one subnet (see §4.1).
- **Integration VPC (spoke)**: LinkEngine's Cloud Run functions (the Publish Function and its four subscriber functions), deliberately separated from the Application VPC — not for an IP-capacity reason (Cloud Run's Direct VPC egress still doesn't consume one IP per concurrent execution the way AWS Lambda's ENI model does), but for network/IAM blast-radius isolation: this is the one compute tier in the platform invoked by externally-triggered partner traffic (LabCorp/Quest/PACS/Surescripts, authenticated by client certificate/API key, not a Meridian identity), distinct from the Application VPC's user- and staff-authenticated traffic. See ADR-022.
- **Data VPC (spoke)**: Cloud SQL for SQL Server, reached over Private Services Access (a VPC peering connection to Google's service-producer network, not a subnet Meridian provisions resources into directly — see §4.1).
- **Shared Services VPC (spoke)**: platform-wide observability and operations tooling — Cloud Logging's logs router, Cloud Monitoring, Cloud DNS private zones, GCP backup tooling, and Secret Manager's private access path — kept in its own spoke since these are consumed by every other spoke, not scoped to one application tier.
- **Landing zone structure**: a Google Cloud Organization with an Infrastructure Folder (network, security-tooling projects) separate from the Workloads Folder this application lives in — see ADR-021's structural note for why this is a *project* boundary on GCP, not an account (AWS) or subscription (Azure) boundary. See ADR-021 for Network Connectivity Center hub-and-spoke vs. plain VPC Peering.

### 4.1 Network Addressing Plan

Named services and boxes on a diagram aren't a network — the same principle `azure-implementation.md` §4.1 and `aws-implementation.md` §4.1 applied. The same non-overlapping CIDR scheme used for the Azure and AWS designs is reused here deliberately, for the same reason: it's already validated not to collide with anything, and using the same ranges across platform implementations makes the eventual Step 10 comparison easier to read.

**A correction worth flagging explicitly, in the opposite direction from the AWS correction.** `aws-implementation.md` §4.1 had to fix a design that used one subnet where AWS actually required three (one per Availability Zone), because an AWS VPC subnet is zone-scoped. GCP has the **opposite** property: a **GCP VPC subnet is a regional resource that spans every zone in the region automatically**, matching Azure's model, not AWS's. A resource pool meant to span 3 zones for resilience needs exactly **one** subnet on GCP, not three — provisioning `subnet-app-zone1/zone2/zone3` the way the AWS design needed per-AZ subnets would be redundant here, not merely unnecessary. The table below reflects that: every tier gets one regional subnet, full stop.

**A revision worth flagging just as explicitly.** An earlier version of this table put LinkEngine's Cloud Run functions in the Application VPC, sharing a subnet with the Portal — correct on IP-capacity grounds (Cloud Run's Direct VPC egress genuinely doesn't need per-tier isolation the way AWS Lambda does), but it missed a separate, legitimate reason to isolate LinkEngine anyway: it's the one compute tier reachable by externally-triggered partner traffic, not Meridian-authenticated users or staff. The table below reflects the corrected design — a dedicated Integration VPC — and folds Apigee's runtime and Citrix into a single consolidated Application VPC subnet, since nothing about sharing a subnet between Compute Engine instances and a Cloud Run service's Direct VPC egress is unsafe on GCP the way it might look coming from AWS/Azure's more subnet-per-tier-by-necessity habits.

| VPC | Address space | Subnet | Range | Purpose |
| --- | --- | --- | --- | --- |
| Inspection VPC (hub) | 10.10.0.0/16 | subnet-hub | 10.10.0.0/24 | NCC hub router appliances, Cloud NGFW endpoints, Cloud VPN/Interconnect attachment — one regional subnet, no per-zone split needed |
| Application VPC | 10.20.0.0/16 | subnet-app | 10.20.1.0/24 | Apigee runtime, the Portal's Cloud Run service (Direct VPC egress), and Citrix/CareLink PM Compute Engine instances plus Cloud Connectors, all in one shared regional subnet (254 usable addresses) — comfortably covers ADR-019's ~125-instance 36-month Citrix ceiling plus connector overhead plus the Portal's 10-instance Cloud Run ceiling, versus the AWS design's separate per-zone subnets for the same tiers |
| Integration VPC | 10.50.0.0/16 | subnet-integration | 10.50.1.0/24 | LinkEngine's Cloud Run functions — the Publish Function and its four subscriber functions — isolated into their own VPC for network/IAM blast-radius reasons (externally-triggered partner traffic), not IP capacity (see ADR-022) |
| Data VPC | 10.30.0.0/16 | subnet-data | 10.30.1.0/24 | Reserved, general-purpose regional subnet for the Data VPC — not yet home to any provisioned resource, held for future data-tier compute (e.g. a Dataflow or BigQuery connector) should one become necessary |

| DR region mirror: Application VPC-DR | 10.120.0.0/16 | subnet-app-dr | 10.120.1.0/24 | `meridian-healthcare-dr-app` project — Compute Engine/Cloud Run failover targets for Portal and Citrix |
| DR region mirror: Data VPC-DR | 10.130.0.0/16 | subnet-data-dr / Private Services Access (peered range) | 10.130.1.0/24 / 10.130.128.0/20 | `meridian-healthcare-dr-data` project — Cloud SQL cross-region read replica target |
| DR region mirror: Shared Services VPC-DR | 10.140.0.0/16 | subnet-shared-dr | 10.140.1.0/24 | `meridian-healthcare-dr-shared` project (§4.2) — DR-side monitoring/logging and backup |

**A gap worth surfacing, not glossing over.** There is deliberately no DR mirror for the Integration VPC in the table above yet — LinkEngine's Cloud Run functions have no pre-provisioned failover target in `us-west1`. That's a real hole in the DR runbook (§12), not a design decision: without it, LinkEngine ingestion has nowhere to fail over to. The natural next block in this numbering scheme is `10.150.0.0/16` (`meridian-healthcare-dr-integration`), following the same one-project-per-spoke pattern as the other three DR mirrors — flagged here for the next diagram/doc pass rather than added unilaterally without a diagram to check it against.

Two controls make this addressable network actually enforce the Zero Trust posture, not just draw it:

- **Route enforcement through the NCC hub**: spoke VPCs' default route targets the Network Connectivity Center hub, which enforces transit through the Inspection VPC's Cloud NGFW before reaching a Cloud NAT gateway or the internet — the GCP-native equivalent of Azure's UDR-forced-tunnel pattern and AWS's Transit Gateway route table association, achieved through NCC hub route policies rather than either of those mechanisms.
- **Firewall policies**, attached at the hierarchical (organization/folder), VPC, or resource-tag level — for example, the Cloud SQL instance's authorized-network/firewall configuration only accepts connections originating from the Citrix, Cloud Run Portal, and Cloud Run LinkEngine service identities, denying everything else by default. This is a genuine model difference worth naming: unlike AWS's split between stateful security groups and stateless NACLs, or Azure's single NSG model, GCP's **hierarchical firewall policies** apply centrally at the organization or folder level (enforced before any VPC-level firewall rule is evaluated), with VPC firewall rules as the second, more granular layer — a two-tier model with a different shape from either sibling platform's.

Private Google Access lets Pub/Sub and Cloud Storage be reached from both spokes without a public IP or a dedicated VPC-endpoint-style subnet the way AWS's interface endpoints needed — Private Google Access is a per-subnet toggle, not a resource that consumes address space of its own.

No detail diagrams exist yet for the addressing plan or deployment topology — hand-drawn diagrams are added incrementally and checked against this document once available, the same standard applied to every diagram in the Azure and AWS sections of this repository.

### 4.2 Governance — Folders and Projects

Landing zone structure isn't just a paragraph — it's a specific Google Cloud Resource Manager hierarchy: a **Security** Folder holding the log-archive and audit projects every workload's logs and Cloud Audit Logs flow into, an **Infrastructure** Folder holding the shared networking project(s) (Network Connectivity Center, Inspection VPC, Cloud Interconnect), and a **Workloads** Folder holding the actual per-environment projects. The Workloads Folder is split finer than one project per environment, mirroring ADR-021's structural note, and finer still than the original AWS-parity count now that the network topology has grown two more spokes: **four Production projects** in the primary region — `meridian-healthcare-prod-app` (Application VPC: Citrix Compute Engine, Cloud Run Portal, Apigee runtime), `meridian-healthcare-prod-integration` (Integration VPC: LinkEngine's Cloud Run functions, isolated for the network/IAM blast-radius reason in §4/ADR-022, not an afterthought), `meridian-healthcare-prod-data` (Data VPC: Cloud SQL), and `meridian-healthcare-shared` (Shared Services VPC: platform-wide logging/monitoring/DNS/backup/Secret Manager) — separating compute, externally-triggered ingest, data, and shared tooling at the project boundary rather than just the VPC boundary, plus one `meridian-healthcare-nonprod` project for Dev/Test/UAT. The Infrastructure Folder adds a `meridian-network` project for the primary region's Inspection VPC and NCC hub. The paired DR region in `us-west1` mirrors three of these four production projects today — `meridian-healthcare-dr-app`, `meridian-healthcare-dr-data`, `meridian-network-dr`, and `meridian-healthcare-dr-shared` — but **not yet a `meridian-healthcare-dr-integration`** mirroring the new Integration VPC; see §4.1's explicit callout of that gap. Ten workload/network projects total across both regions today, growing to eleven once the DR Integration project in §4.1 is added — two more than `aws-implementation.md` §4.2's eight-account structure today, growing to three more once complete. A genuine divergence, not a rounding difference, driven by the Integration VPC and Shared Services VPC splits this design added that the AWS account structure doesn't have an equivalent for. Unlike AWS Control Tower or Azure's Landing Zone Accelerator, this structure isn't provisioned by a single managed console product — see ADR-021's explicit callout of that gap.

## 5. Identity and Security

- Google Cloud Managed Service for Microsoft AD, in a two-way forest trust with Meridian's existing on-prem Active Directory, lets Compute Engine Citrix instances domain-join and clinical staff authenticate with their existing credentials — direct parity with AWS Directory Service and Entra Connect hybrid sync.
- Cloud Identity, layered on top of the directory trust, provides SSO for Google Cloud Console access and Google-hosted resources the platform team itself needs.
- **A gap worth naming plainly, not glossed over — the same gap named for AWS.** Cloud Identity's risk-based/adaptive sign-in and device-compliance evaluation are materially less mature than Microsoft Entra ID P2's Conditional Access and Identity Protection — there is no direct GCP-native equivalent to "block sign-in from a non-compliant device" at the same level of built-in sophistication. Closing that gap fully on GCP, like on AWS, realistically requires a third-party identity/CASB layer (Okta, Duo) or accepting a weaker posture than the Azure design achieves natively. Flagged here for the Step 10 decision matrix, the identical posture ADR-016/ADR-023 already took for their respective platforms.
- Every PaaS service (Apigee, Cloud Run, Pub/Sub, Cloud SQL, Cloud Storage) is reached through **Private Google Access, Direct VPC egress, or Private Services Access** — never the public internet — mirroring the Azure/AWS designs' private-connectivity-everywhere posture.
- Google Cloud Secret Manager holds every credential; Certificate Manager holds every TLS certificate. IAM service accounts (not embedded secrets) let Cloud Run services, Cloud Run functions, and Compute Engine instances authenticate to Secret Manager and to each other — directly retiring the shared/generic service accounts named in the current-state assessment.
- Security Command Center Premium provides workload-level threat detection across the Compute Engine, database, and storage layers, with findings surfaced in one place.
- Patients remain a deliberately separate identity population from staff — see ADR-023. Extending Managed Microsoft AD to also hold ~2 million patient identities was considered and rejected for the same reason ADR-009/ADR-016 rejected it; Identity Platform keeps that consumer population out of the directory that governs clinical-system access.

## 6. Integration — Google Cloud Pub/Sub

HL7 and API events route through Pub/Sub topics, one per message category (lab results, imaging, e-prescribing, appointment events), each with its own subscription carrying a dead-letter policy. Built-in dead-lettering means a failed or malformed message doesn't just disappear — the same direct fix for LinkEngine's current "if CareLink PM is down, the message is lost" behavior the Azure and AWS designs achieve. An ordering key = patient ID preserves message ordering where a downstream consumer needs it. Getting that patient ID onto the message in the first place is a small Cloud Run function **Publish Function** (ADR-025), invoked by Apigee's backend target right after mTLS/quota validation — it parses the raw HL7v2 payload, extracts the patient ID, and publishes to the matching Pub/Sub topic, since Apigee's own policy engine can't reliably do that extraction against pipe-delimited HL7v2 text the way it could against JSON. The subscriber logic that actually reacts to these messages runs on Cloud Run functions, not the Citrix Compute Engine tier — see ADR-022 for why interactive session compute and background message processing are deliberately kept on separate, independently-scaling platforms, the identical reasoning ADR-008/ADR-015 used.

## 7. Observability

Every component above ships logs and metrics to Google Cloud Logging and Cloud Monitoring. Unlike AWS, whose native security-operations stack is four separate purpose-specific services stitched together (Security Lake, GuardDuty, Security Hub, OpenSearch — see `aws-implementation.md` §7), GCP's equivalent is closer to a single integrated product: **Security Command Center (Premium tier)** provides threat detection, vulnerability findings, and a query/dashboard surface in one place, sitting on top of the same Cloud Logging data every other component writes to — closer in shape to Azure's single-product Sentinel than to AWS's four-service composition, worth naming as a genuine structural difference between all three platforms' security-operations stories, not just three vendors' names for the same thing. Cloud Monitoring alerting policies are tied to the same RTO/RPO-relevant signals (replication lag, failed sign-ins, Pub/Sub dead-letter topic depth) that matter operationally, not just infrastructure health.

## 8. Disaster Recovery Implementation

| Element | GCP Mechanism |
| --- | --- |
| Database replication | Cloud SQL native cross-region read replica from the primary instance to `us-west1`, promotable on failover — **a genuine GCP-native capability RDS Custom explicitly lacks** (ADR-013's own flagged gap), so this is a real strength relative to the AWS design, not a wash; see ADR-020 |
| VM tier replication | No fully turnkey, first-party block-level continuous-replication service directly equivalent to AWS Elastic Disaster Recovery exists for Compute Engine today — the realistic approach is a pre-provisioned, scaled-down matching Machine Catalog in `us-west1`, kept current via the same golden-image pipeline used for the primary region, and scaled up on failover. This is a real, named gap relative to AWS DRS's continuous block replication, not glossed over |
| Storage replication | Google Cloud Storage Turbo Replication (for dual-region/multi-region buckets) |
| Messaging | **No native replication at all** — matching infrastructure (topics/subscriptions) is pre-provisioned in `us-west1` via the same IaC, with no message content carried over; see ADR-025's explicit gap callout, the same category of gap ADR-018 named for AWS |
| Failover trigger | Manual-initiated (ADR-004) — an operator triggers Cloud SQL replica promotion and the Compute Engine Machine Catalog cutover through a documented runbook, not an automatic process |
| Traffic cutover | Google Cloud DNS with a failover routing policy, in front of the global external Application Load Balancer |

This is the GCP-specific implementation of the warm-standby topology decided in ADR-004 — the strategy didn't change, only the tooling that realizes it. Two real gaps are named honestly here (no turnkey continuous VM-tier replication service, no native Pub/Sub cross-region replication), alongside one genuine strength (Cloud SQL's native cross-region replica, stronger than RDS Custom's bolted-on DMS approach). Weighed directly in Step 10, not hidden in either direction.

## 9. Infrastructure as Code

Terraform (Google's own published modules, plus the Cloud Foundation Fabric blueprint referenced in ADR-021) is the primary IaC tool for this GCP implementation. Unlike Azure (Bicep) and AWS (CloudFormation/CDK), Google does not publish a first-party declarative IaC language of its own for general resource provisioning — Terraform is GCP's de facto native tool, not merely the cross-platform comparison tool it is for the other two designs. That's worth naming as a genuine difference: `azure-implementation.md` §9 and `aws-implementation.md` §9 both reserve Terraform for the Step 10 cross-platform comparison and use a platform-native language day to day; this document's day-to-day tool and its comparison tool are the same thing.

## 11. End-to-End Transaction Walkthrough

Every component in the service mapping and the deployment diagram exists because it does something in an actual data flow — the same proof exercise `azure-implementation.md` §11 and `aws-implementation.md` §11 ran: trace one real transaction through every hop it touches, including what happens when it fails.

Scenario: a new lab result arrives from LabCorp for an existing patient.

1. LabCorp posts the HL7 v2 result to Apigee over mutual TLS with an API key. Apigee validates the client certificate and key, applies a quota policy, and invokes the `linkengine-publish-function` (Cloud Run function) via a backend target.
2. The Publish Function parses the raw HL7v2 payload, extracts the patient ID, and publishes the message to the `lab-results` Pub/Sub topic using the patient ID as the ordering key so results for the same patient stay ordered. Apigee returns `202 Accepted` to LabCorp once the publish succeeds — LabCorp doesn't wait on downstream processing.
3. On the happy path, the `lab-results` topic's subscription delivers the message to its Cloud Run function subscriber (triggered via Eventarc/push subscription), which writes the structured result to the patient's record in Cloud SQL for SQL Server over a private connection, archives the raw HL7 payload to immutable Cloud Storage, and acknowledges the message on successful completion.
4. On the failure path — for example, the patient ID doesn't match an existing record — the function's invocation fails and the message is redelivered. Pub/Sub retries up to the configured `max delivery attempts`, then the dead-letter policy moves it to the dead-letter topic and a Cloud Monitoring alert fires to on-call, instead of silently dropping it — the direct fix for the current LinkEngine's "if CareLink PM is down, the message is lost" failure mode.
5. Later, when a provider opens the patient's chart in CareLink PM, the query against Cloud SQL returns the record with the new result already in it — the write from step 3 and the read in step 5 are decoupled in time by design, the same "event-driven" property the Azure and AWS designs achieve.

Every hop above also ships logs and metrics to Cloud Logging/Cloud Monitoring, which is what makes the dead-letter alert in step 4 possible in the first place.

## 12. Disaster Recovery Runbook

ADR-004 set the target: warm standby, manual-initiated failover, RTO ≤ 4 hours, RPO ≤ 15 minutes — platform-neutral. Section 8 named the GCP mechanisms, including the gaps (no turnkey continuous VM-tier replication, no native Pub/Sub cross-region replication) alongside the one genuine strength (Cloud SQL's native cross-region replica). What's still missing is proof that those mechanisms, run in the realistic order an on-call engineer would actually run them, fit inside the 4-hour budget.

1. **T+0 to T+15 min** — Cloud Monitoring alerting policies page on-call; the engineer confirms the outage is real and declares a disaster per the documented runbook, rather than failing over on a single alert.
2. **T+15 to T+35 min** — the engineer promotes the Cloud SQL cross-region read replica in `us-west1` to a standalone, writable primary. This step is allotted *less* time than either the Azure or AWS equivalent specifically because Cloud SQL cross-region replica promotion is a native, first-class operation, not a bolted-on CDC pipeline (AWS's DMS-based approach) or an auto-failover group (Azure's turnkey but not meaningfully faster mechanism) — an honest reflection of Section 8's named strength, not an optimistic guess.
3. **T+35 to T+125 min**, run in parallel with database promotion where possible — the engineer brings the pre-provisioned, scaled-down `us-west1` Machine Catalog up to day-one capacity (this step is allotted *more* time than the AWS equivalent's AWS DRS-driven failover specifically because there is no turnkey continuous-replication product doing the heavy lifting here — see Section 8's named gap, an honest margin for a mechanism this design has flagged as less mature) **and** confirms the pre-provisioned Pub/Sub topics/subscriptions in `us-west1` are reachable and correctly configured (there is no failover action to trigger for messaging — the resources already exist, since nothing is replicated into them).
4. **T+125 to T+185 min** — before any traffic is cut over, the engineer runs smoke tests against the secondary region (authentication, database read/write, Pub/Sub publish-and-receive against the DR-region resources) to confirm it's actually healthy, not just "up," and separately initiates source-system reconciliation for the failover window — LabCorp, Quest, and Surescripts are queried for results/messages sent during the gap, the identical reconciliation step ADR-011/ADR-018 already establish. This reconciliation runs in the background and does not block the traffic cutover in step 5.
5. **T+185 to T+215 min** — the engineer updates the Cloud DNS failover routing policy to point at the secondary region's load balancer; once DNS propagates, users are routed to the secondary region.

Total: **215 minutes actual against a 240-minute (4-hour) target** — a margin between the Azure design's 180-minute total and the AWS design's 195-minute total, which tracks directly with Section 8's mixed picture: faster on the database leg (Cloud SQL's native replica), slower on the compute leg (no turnkey continuous VM replication) than AWS. If real-world Machine Catalog rebuild times run longer than this estimate during an actual DR test, this runbook's margin erodes — worth weighing directly in the Step 10 comparison. ## 13. CI/CD and Environment Promotion

Terraform (Section 9) is the authoring tool; this section is how a change actually reaches production, using **Cloud Build** and **Cloud Deploy**. Every change flows through the same landing-zone projects named in Section 4.2: the non-production workload project for Dev and Test/QA, the production workload project for production.

- **On every pull request**: `terraform validate` and `tflint` catch syntax and type errors; a policy check via **Open Policy Agent (OPA)/Conftest against the Terraform plan** (GCP has no direct first-party equivalent to AWS's `cfn-guard` or Azure Policy's deployment-time enforcement baked into the same tool as the IaC language, so this is an added-on, not built-in, control — worth naming honestly) enforces security and architecture rules; `terraform plan` posts the predicted resource changes directly on the PR, so a reviewer sees the actual diff — direct parity with `azure-implementation.md`'s `az deployment what-if` step and `aws-implementation.md`'s CloudFormation change-set step.
- **Human review**: the platform team reviews both the code and the plan output before approving.
- **On merge to main**: Cloud Build deploys to Dev automatically, runs automated smoke tests, then Cloud Deploy stops at a manual approval gate before Test/QA, and a second manual approval gate — paired with a change record — before production. Production deployment ends with a post-deploy validation pass and a Security Command Center posture-compliance check, not just a "deployment succeeded" status.

The two manual gates are deliberate, not a process gap — the identical reasoning `azure-implementation.md` §13 and `aws-implementation.md` §13 applied: infrastructure changes to a clinical system's database or network tier are exactly the kind of change that should require a human decision immediately before it happens, the same reasoning behind DR failover being manual-initiated in ADR-004.
