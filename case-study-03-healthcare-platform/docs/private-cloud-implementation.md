# Private-Cloud Implementation — Meridian Health Network

This document implements the vendor-neutral logical design on a private-cloud platform. It is one of four parallel implementations (Azure, AWS, GCP, private cloud) that will be scored against each other in a weighted decision matrix — nothing here is the final platform choice. The point of building this thoroughly, rather than sketching it, is the same discipline `azure-implementation.md`, `aws-implementation.md`, and `gcp-implementation.md` each applied: a fair comparison requires every option to actually be designed, not guessed at.

This track is structurally different from the other three in one important way, and that difference runs through every section below: "Azure," "AWS," and "GCP" are each a single vendor-neutral thing to implement against — the facility, the hardware, and the managed-service menu are already decided and invisible. "Private cloud" is not. ADR-026 had to decide the platform software (VMware Cloud Foundation) and the physical facility strategy (two commercial colocation facilities) before any of the other seven ADRs in this track (ADR-027 through ADR-033) could even begin — a decision none of the hyperscaler tracks needed to make. VCF is chosen deliberately, not by default: Meridian already runs a live VMware vSphere estate (`current-state.md` §3) with existing staff skills, so this is the smallest real operational-skill jump of the private-cloud alternatives, not a green-field platform switch. Where this design's answer is genuinely "the same idea, self-hosted instead of managed," this document says so plainly; where private cloud's own constraints (no managed-service menu, physical hardware Meridian owns, no built-in CDN/WAF edge) push toward a materially different design — sometimes better, more often carrying real operational burden back onto Meridian's team — this document says that too, with the same honesty every other platform section in this repository applies to its own gaps.

This document covers the platform as a whole — facility and platform-software strategy, service selection, networking, security, DR, IaC. For a deeper, per-application treatment of exactly how each of CareLink PM, MeridianConnect Portal, Telehealth, and LinkEngine is hosted, connects to its data, is reached by users, and scales — see [`application-architecture-private-cloud.md`](application-architecture-private-cloud.md).

Where a decision is genuinely platform-neutral (the migration strategy, the DR topology, the database engine family, the target architecture style), it is not re-litigated here — it's inherited from ADR-001 through ADR-004 unchanged. This document and its ADRs (ADR-026 through ADR-033) only decide the private-cloud-specific *how*.

## 2. Compute — Hosting CareLink PM (see ADR-027)

CareLink PM is a Windows thick-client application currently published via Citrix Virtual Apps 7. The lowest-risk private-cloud implementation keeps that exact delivery model and moves only the infrastructure underneath it onto VCF-managed vSphere VMs. Unlike the Azure, AWS, and even GCP comparisons, a real native alternative genuinely exists here — VMware Horizon, running on the same hypervisor VCF already provides — and ADR-027 weighs it directly rather than dismissing it as unavailable. See ADR-027 for why Citrix is kept anyway, and [`application-architecture-private-cloud.md` §1](application-architecture-private-cloud.md#1-carelink-pm-core-pm-service) for the full Cloud Connector / Machine Catalog / physical-host hosting architecture.

## 3. Database — Self-Managed SQL Server on VCF (see ADR-028)

The logical design (ADR-003) already decided "managed relational, not NoSQL." Every sibling platform answered the follow-on question — which managed tier — from a real menu. Private cloud has no such menu at all: there is no Cloud SQL, no RDS, no Azure SQL Managed Instance equivalent here. See ADR-028 for the full reasoning behind self-managed SQL Server 2022 Enterprise on vSphere VMs, using a native Always On Availability Group for both in-facility HA and cross-facility DR, and for why this is named as the single most consequential operational-burden difference in the entire private-cloud track. Both CareLink PM and MeridianConnect Portal use this same instance, as separate databases — see `application-architecture-private-cloud.md` for exactly how each application connects to it.

## 4. Networking and Landing Zone

- **Management segment (hub)**: vCenter, NSX Manager cluster, SDDC Manager, and the Aria Suite — the VCF platform's own control plane, plus remote administrative access.
- **Application segment (spoke)**: the API gateway runtime, the Portal's Tanzu-hosted workload, and Citrix Cloud Connectors/VDA session hosts — the platform's user-and-staff-facing compute, sharing one segment (see §4.1).
- **Integration segment (spoke)**: LinkEngine's Tanzu-hosted subscriber workloads, deliberately separated from the Application segment for the same externally-triggered-traffic trust-boundary reason ADR-022/ADR-015/ADR-008 gave on every sibling platform. See ADR-030.
- **Data segment (spoke)**: the SQL Server Always On VMs (ADR-028).
- **Landing zone structure**: a VCF Management Workload Domain, separate from the Production VI Workload Domain the application tiers actually run in — see ADR-026 and ADR-029 for the Tier-0/Tier-1 NSX hub-and-spoke implementation of this shape.

### 4.1 Network Addressing Plan

The same non-overlapping CIDR scheme used across the Azure, AWS, and GCP tracks is reused here deliberately, for the identical reason `gcp-implementation.md` §4.1 gave: it's already validated not to collide with anything, and using the same ranges across every platform implementation makes the Step 10 comparison easier to read. See ADR-029's Proposed Configuration table for the full segment/range breakdown across both the Columbus (primary) and Dallas (DR) facilities.

**A structural point worth naming, not buried in the ADR alone.** Unlike a hyperscaler VPC/VNet subnet, an NSX segment has no inherent "regional" or "zonal" scoping property to reason about at all — it's simply a logical Layer 2/3 construct the Tier-1 gateway owns, spanning however many ESXi hosts the Workload Domain contains. There is no equivalent of the AWS-subnet-is-zonal / Azure-and-GCP-subnet-is-regional distinction that occupied real space in `aws-implementation.md` §4.1 and `gcp-implementation.md` §4.1 — one segment per tier is simply correct, with resilience coming from vSphere DRS anti-affinity spreading VMs across hosts (ADR-027), not from a subnet-to-availability-zone mapping that doesn't exist in this model.

### 4.2 Governance — VCF Workload Domains

Landing zone structure here is a VCF Workload Domain hierarchy, not a management-group/subscription (Azure) or organization/folder/project (GCP) hierarchy: a **Management Domain** (vCenter, NSX Manager, SDDC Manager, Aria Suite — the platform's own control plane, isolated from application workloads) and a **Production VI Workload Domain** (the actual CareLink PM, SQL Server, Tanzu, and NSX Edge workloads) at each facility, plus a smaller **Non-Production VI Workload Domain** for Dev/Test/UAT at the primary facility only. Unlike AWS Control Tower, Azure's Landing Zone Accelerator, or even GCP's open-source Cloud Foundation Fabric blueprint, VMware does not ship any turnkey landing-zone automation product at all for VCF — Aria Automation provides a self-service catalog and policy-as-code enforcement once configured, but the Workload Domain structure itself, and the governance policies applied to it, are built and maintained entirely by Meridian's own team from the ground up. **This is a genuine operational-maturity gap worth naming plainly, one step further back from even GCP's own named gap** (`gcp-implementation.md` §4.2, which at least has an open-source blueprint to start from) — flagged here for the Step 10 comparison, not assumed away.

## 5. Identity and Security

- The existing on-prem Active Directory forest is reached directly by VCF-managed VMs — no hybrid-identity bridge product is needed, a genuine simplification relative to every sibling platform (see ADR-031's Context).
- Patients authenticate against a managed SaaS CIAM product, kept deliberately separate from workforce identity — see ADR-031, including the honest reversal of this track's usual "keep it in-house" posture and why.
- **A gap worth naming plainly, the same discipline every sibling platform's Section 5 applies to its own identity gap.** Active Directory's own native conditional-access capability is materially behind Microsoft Entra ID P2's — the identical posture gap ADR-009 never had to name (Azure gets Entra ID P2 natively) but ADR-016 and ADR-023 both had to name for AWS and GCP. Closing it fully here, as on AWS and GCP, realistically means a third-party identity/CASB layer (Okta, Duo) layered in front of AD authentication for workforce access — a real, not cosmetic, decision point deferred to Section 14.
- Every internal service (the API gateway, Tanzu workloads, SQL Server) is reached over the private NSX fabric — never the public internet — mirroring the private-connectivity-everywhere posture of every sibling design.
- HashiCorp Vault (or a comparable self-hosted secrets manager) holds every credential; a dedicated certificate-management process handles TLS certificates. Service accounts (not embedded secrets) let Tanzu workloads and VMs authenticate to Vault and to each other — directly retiring the shared/generic service accounts named in the current-state assessment.
- A dedicated SIEM product (see Section 7) layered on top of Aria Operations/Log Insight provides the threat-detection capability the sibling platforms get from a single native product (Security Command Center, Sentinel, or the AWS four-service stack).

## 6. Integration — RabbitMQ

HL7 and API events route through RabbitMQ exchanges, one per message category (lab results, imaging, e-prescribing, appointment events), each with a dead-letter exchange. A patient-ID-based routing key preserves message ordering where a downstream consumer needs it. Getting that patient ID onto the message in the first place is a small Tanzu-hosted **Publish Service** (ADR-033), invoked by the API gateway's backend route right after mTLS/quota validation — it parses the raw HL7v2 payload, extracts the patient ID, and publishes to the matching exchange, since the API gateway's own policy engine can't reliably do that extraction against pipe-delimited HL7v2 text, the identical real constraint named on every sibling platform. The subscriber logic that actually reacts to these messages runs on Tanzu, scaled by KEDA against queue depth — not the Citrix VM tier — see ADR-030 for why interactive session compute and background message processing are deliberately kept on separate, independently-scaling platforms.

## 7. Observability

Every component above ships logs and metrics to Aria Log Insight, with Aria Operations providing infrastructure and application-level monitoring — both bundled as part of the VCF platform license ADR-026 already committed to, a genuine simplification worth naming: unlike AWS's four-service security-operations stack or even GCP's still-separate Security Command Center subscription, the base observability layer here comes with the platform, not as an additional service to provision. **What is not bundled, and needs a separate decision this document names rather than glosses over**: neither Aria Operations nor Aria Log Insight is a SIEM/threat-detection product — closing that gap (the same "no SIEM, manual multi-system review" gap named in `current-state.md`) requires layering a dedicated SIEM product (e.g., Elastic Security, or a comparable self-hosted or SaaS option) on top, which Meridian must select, deploy, and operate directly. This is deferred to Section 14 as a real decision point, not resolved here.

## 8. Disaster Recovery Implementation

| Element | Private-Cloud Mechanism |
| --- | --- |
| Database replication | SQL Server Always On asynchronous replica, Columbus → Dallas — a native database feature Meridian operates directly, not a managed cross-region replica the platform provides (contrast ADR-020's genuine GCP-native strength) |
| VM tier replication (Citrix, Tanzu) | No replication in the streaming sense — the DR facility runs its own pre-provisioned, full-target-capacity Machine Catalog and Tanzu cluster (ADR-026), kept current via the same configuration-management pipeline used for the primary facility (Section 9) |
| Storage replication | Veeam Backup & Replication, cross-facility replication to an immutable repository at the DR facility (ADR-028) |
| Messaging | **No native replication at all** — matching exchanges/queues pre-provisioned in Dallas via the same configuration-management tooling, with no message content carried over; see ADR-033's explicit gap callout, the same category of gap ADR-018/ADR-025 named for their platforms |
| Failover trigger | Manual-initiated (ADR-004) — an operator promotes the SQL Server Always On replica and redirects traffic through a documented runbook, not an automatic process |
| Traffic cutover | DNS-based failover (an external, geo-aware DNS/CDN provider — the same CDN/WAF product from ADR-032 — updates its origin pool) |

**The structural point that makes this section different from every sibling platform's, stated once here and inherited by every other DR-adjacent decision in this track.** A hyperscaler's "warm standby, scale up on failover" pattern is fundamentally elastic — the DR region's capacity ceiling is however much the platform will let you provision on demand. A private-cloud DR facility's capacity ceiling is whatever physical hardware is already racked, powered, and licensed there *before* the disaster — nothing can be procured, shipped, and installed mid-incident. ADR-026 already made the resulting decision explicit: the Dallas facility is provisioned to match full 36-month target capacity from day one, not scaled up incrementally. That closes the elasticity gap at real, ongoing capital cost (idle capacity paid for from day one, not grown into) rather than at RTO risk — a trade-off unique to this track, and one that should be weighed with real financial weight in Step 13, not treated as equivalent to the "idle standby capacity" cost ADR-004 already named generically for every platform.

## 9. Infrastructure as Code

Terraform — via the officially-supported vSphere, NSX-T, and VCF providers — is the primary IaC tool for this implementation, continuing the same tool used across the Azure, AWS, and GCP tracks for their cross-platform Step 10 comparison, and directly consistent with the reference guide's own observation that Terraform is "the one IaC tool with mature providers for Azure, AWS, GCP, VMware, and Kubernetes alike." Unlike the hyperscaler tracks, where Terraform is reserved for cross-platform comparison while a platform-native language (Bicep, CloudFormation/CDK) handles day-to-day provisioning, there is no private-cloud-native declarative IaC language at all — Terraform is this track's only realistic choice, day-to-day and for comparison alike, the identical positioning `gcp-implementation.md` §9 named for Terraform on GCP. Ansible handles in-guest configuration management (OS hardening, SQL Server/RabbitMQ/Vault configuration) that Terraform's resource-provisioning model doesn't cover — a second tool this track needs that the fully-managed hyperscaler services mostly abstract away.

## 11. End-to-End Transaction Walkthrough

The same proof exercise every sibling implementation document ran: trace one real transaction through every hop it touches, including what happens when it fails.

Scenario: a new lab result arrives from LabCorp for an existing patient.

1. LabCorp posts the HL7 v2 result to the API gateway over mutual TLS with an API key. The gateway validates the client certificate and key, applies a quota policy, and invokes the Publish Service (a Tanzu-hosted workload) via a backend route.
2. The Publish Service parses the raw HL7v2 payload, extracts the patient ID, and publishes the message to the `lab-results` RabbitMQ exchange using the patient ID as the routing key so results for the same patient stay ordered. The gateway returns `202 Accepted` to LabCorp once the publish succeeds — LabCorp doesn't wait on downstream processing.
3. On the happy path, the `lab-results` queue delivers the message to its Tanzu-hosted subscriber Deployment, which writes the structured result to the patient's record in SQL Server over the private NSX fabric, archives the raw HL7 payload to the object-storage layer, and acknowledges the message on successful completion.
4. On the failure path — for example, the patient ID doesn't match an existing record — the consumer's processing fails and the message is redelivered. RabbitMQ retries up to the configured delivery limit, then the dead-letter exchange captures it and an Aria Operations/SIEM alert fires to on-call, instead of silently dropping it — the direct fix for the current LinkEngine's "if CareLink PM is down, the message is lost" failure mode.
5. Later, when a provider opens the patient's chart in CareLink PM, the query against SQL Server returns the record with the new result already in it — the write from step 3 and the read in step 5 are decoupled in time by design, the same event-driven property every sibling platform achieves.

Every hop above also ships logs and metrics to Aria Log Insight, which is what makes the dead-letter alert in step 4 possible in the first place.

## 12. Disaster Recovery Runbook

ADR-004 set the target: warm standby, manual-initiated failover, RTO ≤ 4 hours, RPO ≤ 15 minutes — platform-neutral. Section 8 named the private-cloud mechanisms, including the structural gap (no elastic scale-up, hardware pre-provisioned at full capacity instead) that shapes every step below differently than on the hyperscaler tracks.

1. **T+0 to T+15 min** — Aria Operations/SIEM alerting pages on-call; the engineer confirms the outage is real and declares a disaster per the documented runbook, rather than failing over on a single alert.
2. **T+15 to T+45 min** — the engineer promotes the SQL Server Always On asynchronous replica in the Dallas facility to a standalone, writable primary. This step is allotted *more* time than any of the Azure, AWS, or GCP equivalents specifically because this is a manually-operated database failover, not a managed service's native promotion API — an honest reflection of ADR-028's named burden, not an optimistic guess.
3. **T+45 to T+95 min**, run in parallel where possible — the engineer confirms the pre-provisioned Dallas Tanzu cluster and RabbitMQ cluster are healthy and reachable (there is comparatively little to "bring up" here, since ADR-026 already deliberately provisioned the DR facility to full capacity rather than a scaled-down pilot light — the one place this track's runbook is genuinely *faster* than a hyperscaler's compute-tier scale-up step, because there's no scaling operation to wait on at all, just a health check).
4. **T+95 to T+155 min** — before any traffic is cut over, the engineer runs smoke tests against the Dallas facility (AD authentication reachability, database read/write, RabbitMQ publish-and-receive against the DR-facility resources) to confirm it's actually healthy, not just "up," and separately initiates source-system reconciliation for the failover window — LabCorp, Quest, and Surescripts are queried for results/messages sent during the gap, the identical reconciliation step every sibling platform already establishes. This reconciliation runs in the background and does not block the traffic cutover in step 5.
5. **T+155 to T+185 min** — the engineer updates the CDN/WAF provider's origin pool (Section 8) to point at the Dallas facility's load balancer; once DNS propagates, users are routed to the secondary facility.

Total: **185 minutes actual against a 240-minute (4-hour) target** — the largest margin of any of the four platform tracks, but for a reason worth stating honestly rather than claiming as unqualified superiority: it's fast specifically because there's no compute-tier scale-up step to wait on (the DR facility is already at full capacity, per ADR-026's real, ongoing capital cost), and slower on the one step (database promotion) that's manually operated rather than API-driven. The margin is real, but it was bought with standing infrastructure spend the hyperscaler tracks don't carry — a trade-off, not a free win, and it should be weighed as such in Step 10 alongside Step 13's cost numbers once they exist. ## 13. CI/CD and Environment Promotion

Terraform (Section 9) is the authoring tool; Ansible handles in-guest configuration. A self-hosted CI/CD tool (e.g., GitLab CI or Jenkins, running on the Tanzu platform itself) orchestrates the pipeline — deliberately self-hosted rather than a SaaS CI/CD product, consistent with keeping build/deploy tooling for infrastructure changes inside the same trust boundary as the infrastructure it changes, unlike the CIAM and CDN/WAF decisions (ADR-031/ADR-032) where this design deliberately chose to go external.

- **On every merge request**: `terraform validate` and `tflint` catch syntax and type errors; a policy check via Open Policy Agent (OPA)/Conftest against the Terraform plan (there is no first-party policy-as-code product bundled with VCF the way Azure Policy is bundled with Bicep — Aria Automation provides a self-service catalog and guardrails once configured, but not the same deployment-time plan-level enforcement) enforces security and architecture rules; `terraform plan` posts the predicted resource changes directly on the merge request, so a reviewer sees the actual diff — direct parity with the equivalent step on every sibling platform.
- **Human review**: the platform team reviews both the code and the plan output before approving.
- **On merge to main**: the pipeline deploys to the Non-Production Workload Domain automatically, runs automated smoke tests, then stops at a manual approval gate before a production deployment window, and a second manual approval gate — paired with a change record — before the change actually lands on the Production VI Workload Domain. Production deployment ends with a post-deploy validation pass, not just a "deployment succeeded" status.

The two manual gates are deliberate, not a process gap — the identical reasoning every sibling platform's CI/CD section applied: infrastructure changes to a clinical system's database or network tier are exactly the kind of change that should require a human decision immediately before it happens, the same reasoning behind DR failover being manual-initiated in ADR-004.
