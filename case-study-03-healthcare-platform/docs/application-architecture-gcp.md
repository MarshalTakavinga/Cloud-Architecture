# Per-Application Implementation Architecture — Meridian Health Network on GCP

`docs/gcp-implementation.md` maps every logical component to a GCP service. This document goes one level deeper, mirroring `application-architecture.md`/`application-architecture-aws.md`'s structure: for each application, it answers the questions a design review actually asks — what compute it runs on and how many instances, exactly how it reaches its database, whether it's public or private and who can reach it, and how it scales and survives a failure. The same four applications are covered: CareLink PM (the replatformed vendor core), MeridianConnect Portal (the refactored owned application), Telehealth (the repurchased third-party service), and LinkEngine (the refactored integration layer).

## 1. CareLink PM (Core PM Service)

**Migration strategy:** Replatform (ADR-001, platform-neutral). **Compute:** Citrix Virtual Apps and Desktops on Google Compute Engine (ADR-019). **Database:** Cloud SQL for SQL Server, Regional HA (ADR-020) — this is the direct answer to "which GCP database service and why": Cloud SQL is GCP's only managed SQL Server tier, chosen with a real, named compatibility risk accepted up front rather than discovered mid-migration, since GCP (unlike AWS's RDS Custom) has no OS-access middle tier to fall back to without going fully self-managed.

**Hosting architecture.** CareLink PM's compute is not a simple "instances behind a load balancer" — Citrix has its own control plane, and the implementation decision from ADR-019 was to keep using it rather than replace it, exactly as ADR-005/ADR-012 decided for Azure and AWS. Meridian's existing Citrix Cloud subscription remains the control plane (session brokering, published app catalog); only the infrastructure Citrix actually runs sessions on moves to GCP. Concretely:

- **Cloud Connectors** — four Compute Engine instances (one per zone plus a spare), in `subnet-app`, Application VPC (`10.20.0.0/16`), alongside the VDA session hosts, the Portal's Cloud Run service, and the Apigee runtime (unlike AWS, which needed a dedicated per-AZ subnet for Cloud Connectors separate from session hosts, GCP's single consolidated regional subnet holds all of it — see ADR-019 and `gcp-implementation.md` §4.1). They make outbound-only connections to Citrix Cloud; nothing inbound from the internet ever reaches them directly. See ADR-019's Proposed Configuration for why this is four, not the commonly-cited minimum of two.
- **VDA session hosts** — the actual CareLink PM delivery machines, organized into a Machine Catalog spread across three zones, `n2-standard-8` instances, Windows Server 2022. The catalog autoscales between an off-peak floor of roughly 6-9 instances and a day-one peak of roughly 45 instances (today's ~1,800 concurrent sessions), sized up to a 36-month target ceiling of roughly 125 instances (5,000 concurrent sessions) — see ADR-019's Proposed Configuration for the concurrency data and sizing assumptions, reused unchanged from ADR-005/ADR-012 since the demand-side figures are platform-independent. This is where clinicians' sessions actually run.
- **Database connectivity** — each VDA connects to Cloud SQL for SQL Server over a private path (Private Services Access, not a subnet Meridian provisions into directly — see `gcp-implementation.md` §4.1), TDS port 1433, TLS-encrypted. The database login is retrieved from Secret Manager at boot via the instance's attached service account.

**Public or private, and how staff reach it.** Nothing in the application or data VPC has a public IP. A provider's device reaches Citrix Cloud's Gateway Service over the public internet (HDX protocol over TLS 443) — that's the only public-facing hop in the whole path. Citrix Cloud brokers the session and connects inward to a Cloud Connector, which routes to an available VDA. The connection into GCP is always broker-initiated from the Cloud Connector outward; a clinic never opens an inbound port to Meridian's GCP network, which is what makes this compatible with the Zero Trust posture from ADR-002 without a VPN — identical to the Azure and AWS designs.

**Scaling and HA.** Citrix's own autoscale (not Compute Engine Managed Instance Group autoscaling) power-manages the VDA pool: additional session hosts spin up per zone on a schedule matched to clinic hours, and scale back down overnight. High availability comes from spreading the Machine Catalog across three zones — losing one zone removes roughly a third of capacity, not all of it — plus redundant Cloud Connectors so the control-plane bridge itself isn't a single point of failure.

## 2. MeridianConnect Portal

**Migration strategy:** Refactor (ADR-002, platform-neutral) — this is Meridian-owned code, so unlike CareLink PM it can actually be rebuilt for the target platform. **Compute:** Google Cloud Run (ADR-024) — chosen over GKE (staffing) and Compute Engine (unneeded operational surface); unlike the Azure/AWS Portal ADRs, the serverless option here is also the *most* proven option, not a newer alternative being weighed cautiously. **Database:** the same Cloud SQL for SQL Server instance, a separate database within it.

**Hosting architecture.** The Cloud Run service runs zone-redundant instances automatically (Cloud Run is a regional service, inherently spanning the zones in that region — there's no explicit "spread across 3 zones" configuration step the way Compute Engine or AWS/Azure's VM-based tiers needed), reached via Direct VPC egress into the Application VPC, which is what lets it reach Cloud SQL over a private path instead of a public connection string. A global external Application Load Balancer sits in front of it as the actual public entry point, with Cloud Armor attached running a managed WAF rule set and Cloud CDN caching static assets, reaching Cloud Run through a Serverless Network Endpoint Group rather than a public URL directly — the load balancer's backend configuration is what makes this a VPC-private-origin pattern, the direct analog to CloudFront's VPC origin and Front Door's Private Link origin. The database connection string itself is never stored in the container image or environment directly; it's pulled from Secret Manager at startup, resolved using the Cloud Run service's attached IAM service account.

**Public or private, and how patients and staff reach it.** This one genuinely is public-facing, because patients need to reach it from their own devices with no VPN or corporate network — but "public-facing" means the load balancer is public, not that the Cloud Run service itself is reachable directly. Two distinct identity providers sit behind the login screen: patients authenticate against **Google Cloud Identity Platform** (ADR-023), a consumer identity product kept deliberately separate from the workforce directory; providers and staff authenticate against **Google Cloud Managed Service for Microsoft AD** (with MFA enforced via Cloud Identity) used everywhere else in this design. The Portal itself decides which federation to invoke based on which login path the user takes.

**Scaling and HA.** Autoscale rules target 3 to 10 Cloud Run instances based on concurrent request count per instance, covering both steady traffic and spikes (open-enrollment periods, a weather event driving a surge in appointment rescheduling). Unlike ADR-010/ADR-017's floor of 3, which was explicitly a zone-coverage requirement (one task per AZ), the floor here is kept at 3 for direct comparability with the sibling ADRs' numbers, not because GCP forces it — see ADR-024's Proposed Configuration for how the ceiling was estimated from the same patient population and appointment data used throughout this case study. Zone redundancy is inherent to Cloud Run's regional model; the load balancer's own health-check-driven failover and the paired-region warm standby (ADR-004) handle a full regional failure.

## 3. Telehealth Service

**Migration strategy:** Repurchase (ADR-002, platform-neutral) — a deliberate non-build. This section exists mainly to be explicit about what Meridian does *not* host, since that's as much a design decision as anything built — unchanged from the Azure and AWS designs, because Repurchase means there's very little that's platform-specific to begin with.

**Hosting architecture.** There isn't one, on Meridian's side — that's the point of Repurchase. The vendor's video/call platform and scheduling API run entirely on the vendor's own infrastructure. MeridianConnect Portal launches a session using the vendor's SDK or a deep link; from that point, video and audio media flow **directly between the patient's or provider's device and the vendor's infrastructure**, never proxied through Meridian's VPC or the load balancer. That's a deliberate choice, not an oversight: real-time media is latency- and bandwidth-sensitive in a way that makes routing it through an extra hop actively harmful, and Meridian has no compliance reason to intercept it — the vendor is contractually the business associate responsible for that traffic under the BAA.

**What does touch Meridian's GCP environment:** SSO federation (the vendor is configured as a SAML/OIDC relying party against Meridian's Identity Platform/Managed Microsoft AD setup, so nobody needs a separate telehealth password) and a narrow appointment-sync integration — inbound webhooks for status changes and outbound API calls for scheduling — brokered through Apigee like any other external partner integration.

**Public or private:** Apigee's webhook endpoint is necessarily public (the vendor calls it from outside Meridian's network), secured with signature validation and an API key held in Secret Manager, exactly like the LabCorp/Quest integration path in Section 4.

**Scaling and HA:** not Meridian's concern for the vendor side — that's covered by the vendor's own SLA, which is exactly why Repurchase was the right call for a component with no clinical-record ownership implications, regardless of which cloud platform hosts everything else.

## 4. LinkEngine (Integration / Event Bus)

**Migration strategy:** Refactor (ADR-002, platform-neutral) — already message-based on-prem, rebuilt on managed infrastructure. **Messaging platform:** Google Cloud Pub/Sub (ADR-025) — this is the direct answer to "which messaging solution": chosen over Cloud Tasks and self-managed Kafka specifically because per-patient ordering keys and dead-lettering are native Pub/Sub subscription features, and because a single Pub/Sub topic with multiple subscriptions does the fan-out-plus-durable-queue job AWS needed two services (SNS+SQS) to do — see ADR-025's explicit callout of that simplification. One topic per HL7 message category (lab results, imaging, e-prescribing, appointment events), each with a dedicated subscription carrying dead-lettering and ordering-key-based per-patient delivery.

**Processing compute.** This is the piece that was previously undecided: something has to actually run the subscriber code that reacts to a new message. ADR-022 decides that's **Cloud Run functions, one function per subscription, max instances 20, min instances 1** — deliberately *not* the Citrix Compute Engine tier that hosts CareLink PM, even though those instances are already connected to the data VPC. The reasoning: Citrix's autoscaling is tuned for interactive clinical session load, which follows a completely different pattern from message-processing load. Keeping them separate means each scales on the signal that actually matters to it — the identical reasoning ADR-008/ADR-015 used. Each function keeps 1 min-instance warm (avoiding cold-start on clinically time-sensitive categories like lab results and e-prescribing) and can burst to a max-instances ceiling of 20 during a backlog catch-up; delivery is kept single-message-at-a-time per ordering key to avoid breaking per-patient ordering — see ADR-022's Proposed Configuration for the full reasoning.

**Network placement: isolated, but not for the reason AWS needed isolation.** `application-architecture-aws.md` §4 had to isolate LinkEngine's Lambda functions into their own dedicated subnets because each concurrent Lambda execution consumes a subnet IP address for the duration of its VPC-attached ENI — a real capacity constraint. Cloud Run's Direct VPC egress has no equivalent per-execution IP cost, so that specific AWS constraint doesn't transfer to GCP. LinkEngine's Cloud Run functions (the Publish Function and its four subscribers) still run in their own dedicated **Integration VPC** (`subnet-integration`, one regional subnet — see `gcp-implementation.md` §4.1), separate from the Application VPC that hosts Apigee's runtime, the Portal's Cloud Run service, and Citrix — but the reason is network/IAM blast-radius isolation, not IP capacity: LinkEngine's Publish Function is the one compute tier in this design invoked by externally-triggered partner traffic (client certificate/API key via Apigee), not a Meridian-authenticated user or staff member, a materially different trust boundary from what the Application VPC hosts. See ADR-022 for the full reasoning, including the earlier version of this design that conflated the two questions.

**Message flow.** An external system (LabCorp, Quest, a hospital PACS, Surescripts) posts to Apigee over mutual TLS; Apigee validates the client certificate and applies a quota policy, then invokes the **Publish Function** (Cloud Run function, ADR-025) via a backend target. The Publish Function parses the raw HL7v2 message, extracts the patient ID, determines which of the four message categories it belongs to, and publishes to the matching Pub/Sub topic using that patient ID as the ordering key, so multiple messages for the same patient stay ordered — this parsing step exists because Apigee's policy engine works against JSON/XML transforms and can't reliably extract a field from raw pipe-delimited HL7v2 text, the identical real constraint ADR-018 named for AWS's API Gateway mapping templates. The topic's subscription delivers the message to its Cloud Run function subscriber (triggered via Eventarc), which writes the structured result into Cloud SQL for SQL Server over a private path, archives the raw HL7 payload to immutable Cloud Storage, then acknowledges the message on success. If processing fails — most commonly a patient ID that doesn't match an existing record — the message is redelivered, retried up to the configured `max delivery attempts`, then moved to the dead-letter topic with a Cloud Monitoring alert to on-call, instead of silently disappearing the way the current on-prem LinkEngine does when CareLink PM is unreachable.

**Public or private:** only Apigee's ingress is public-facing (secured with mutual TLS); Pub/Sub, the Cloud Run functions, and the data-tier writes all stay inside the private VPC.

**Scaling and HA:** each Cloud Run function scales independently on its own subscription's backlog; Pub/Sub is inherently multi-zone within its region with no tier decision required to get that redundancy, independent of any single subscriber's health.

## 5. Summary — public exposure and identity per application

| Application | Public entry point | Identity | Private data path |
| --- | --- | --- | --- |
| CareLink PM | Citrix Cloud Gateway Service (SaaS, not Meridian's GCP project) | Workforce Managed Microsoft AD, via Citrix's own auth integration | Cloud Connector → VDA → Cloud SQL, all private |
| MeridianConnect Portal | Global external Application Load Balancer (Cloud Armor, Serverless NEG to Cloud Run) | Identity Platform (patients) + Managed Microsoft AD/Cloud Identity (staff) | Cloud Run → Cloud SQL, private VPC path |
| Telehealth | Vendor's own infrastructure (video/media); Apigee webhook (sync only) | SSO federated from Identity Platform/Managed Microsoft AD | N/A — vendor-hosted |
| LinkEngine | Apigee (mutual TLS) | Client certificate / API key, not user identity | Apigee → Cloud Run (Publish Function) → Pub/Sub → Cloud Run (subscribers) → Cloud SQL / Cloud Storage, all private |

No application in this design has a database, storage bucket, or compute tier reachable directly from the public internet — every public entry point is a gateway (Citrix Cloud, the global external ALB, or Apigee) that terminates public traffic and continues over a private path from there. Identical posture to the Azure and AWS designs; only the specific services differ.
