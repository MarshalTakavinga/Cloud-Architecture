### ADR-021: GCP network topology

**Context:**
The logical design carries forward Meridian's existing hub-and-spoke mental model — platform-neutral (ADR-007 for Azure, ADR-014 for AWS). GCP's networking primitives are genuinely different from both: a GCP VPC network is a **global** resource (not regional, the way an Azure VNet or AWS VPC is), and GCP's native network-to-network connectivity option, VPC Peering, is **not transitive** — a network peered to the hub cannot reach another network peered to that same hub through it, unlike Azure VNet peering (which a hub can be configured, via UDRs, to make transitive) or AWS Transit Gateway (natively transitive by design). That non-transitivity isn't a minor footnote here: this design's whole point is that spoke traffic routes *through* the hub's inspection point, which plain VPC Peering structurally cannot do.

**Options considered:**
- Plain VPC Peering between a hub network and application/data spoke networks
- Network Connectivity Center (NCC) — Google's managed, purpose-built transitive hub, connecting VPC spokes (and, later, on-prem/other-cloud sites) through a central hub resource
- A single flat VPC network, no segmentation

**Decision:** Network Connectivity Center hub, with an Inspection VPC and Application/Data VPCs attached as spokes.

**Rationale:**
A flat, unsegmented network is ruled out for the same reason it was never on the table for Azure or AWS — it carries forward the current-state's flat-VLAN weakness (Section 4 of `current-state.md`) into the cloud instead of fixing it, and it's incompatible with the Zero Trust posture ADR-002 already decided. Between the two segmented options, plain VPC Peering looks like the obvious first choice — it's simpler and it's what ADR-007 essentially chose for Azure (VNet peering) — but the non-transitivity problem named in Context is a real blocker, not a style preference: Application VPC traffic that needs to egress through the Inspection VPC's firewall, and Data VPC traffic reached from Application VPC resources, both require routing *through* the hub, which peering alone cannot provide without a costly, brittle full-mesh of peering connections between every spoke pair (defeating the point of having a hub at all). Network Connectivity Center is Google's purpose-built answer to exactly this problem: spokes attach to an NCC hub, and the hub can enforce that all inter-spoke and spoke-to-internet traffic transits a router appliance or, for this design, the Inspection VPC's firewall — the direct structural analog to AWS Transit Gateway + Inspection VPC (ADR-014) and Azure's hub VNet (ADR-007), reached for a GCP-specific technical reason rather than because the sibling platforms have something that looks similar.

**Trade-off:**
NCC is a comparatively newer product in Google's networking portfolio than Transit Gateway or VNet peering are on their respective platforms, and it adds a hub resource to operate and monitor that plain peering wouldn't require. Accepted because the alternative — a peering full-mesh, or a network that can't actually enforce hub-transit inspection — works against this design's core Zero Trust requirement, not just its tidiness. Revisit if Meridian's GCP footprint stays small enough, long enough, that the operational overhead of the hub genuinely isn't earning its keep — the same re-evaluation posture ADR-007 named for Virtual WAN.

**Status:** Proposed

**A structural note worth naming explicitly, mirroring ADR-014's for AWS.** GCP's isolation boundary for workload separation is the **project**, not an account (AWS) or a subscription (Azure) — projects are grouped under **folders**, which sit under an **organization**. In practice this design goes a step finer than one project per environment, for the identical reason ADR-014 gave for AWS: the Workloads folder splits Production into two projects — `meridian-healthcare-prod-app` (Application VPC — Compute Engine Citrix tier, Cloud Run Portal, Cloud Run functions for LinkEngine) and `meridian-healthcare-prod-data` (Data VPC — Cloud SQL) — so compute and data have independent project-level blast-radius and IAM boundaries, plus a `meridian-healthcare-nonprod` project for Dev/Test/UAT. The Infrastructure folder holds `meridian-network` (the Inspection VPC, NCC hub, Cloud NGFW) as its own project. The paired DR region mirrors that same four-project pattern rather than collapsing into one DR project: `meridian-healthcare-dr-app`, `meridian-healthcare-dr-data`, `meridian-network-dr`, and `meridian-healthcare-dr-shared` for cross-cutting DR tooling. Eight workload/network projects across both regions in total — the same count ADR-014 reached for AWS, because the underlying reasoning (separate compute/data blast radius, mirror the DR region rather than collapsing it) is genuinely platform-neutral; only the boundary primitive (project, not account) differs. **A second, real difference worth naming honestly:** unlike AWS Control Tower or Azure's Landing Zone Accelerator, Google does not ship a single, fully-managed console product that provisions this whole structure turnkey — Google's guidance here is the [Cloud Foundation Fabric / "enterprise foundations" blueprint](https://cloud.google.com/architecture/security-foundations), delivered as open-source Terraform the team applies itself, not a managed service. This is a genuine operational-maturity gap relative to the AWS and Azure designs, flagged here for the Step 10 comparison rather than assumed away.
