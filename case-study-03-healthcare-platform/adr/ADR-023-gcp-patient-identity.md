### ADR-023: Identity provider for patient-facing authentication on GCP

**Context:**
ADR-002's Zero Trust decision assumed a single identity provider verifying every call. That holds for staff and providers, represented in Meridian's on-prem Active Directory and extended into GCP via **Google Cloud Managed Service for Microsoft AD** (two-way trust to the existing forest, the direct GCP analog to AWS Directory Service for Microsoft AD and Azure's Entra Connect hybrid sync). Patients are not — they have no corporate directory account, and putting them in one would be both wrong and a security problem, the identical framing ADR-009 used for Azure and ADR-016 used for AWS.

**Options considered:**
- Extend Google Cloud Managed Service for Microsoft AD / Cloud Identity to also hold patient accounts
- Google Cloud Identity Platform — a separate, consumer-facing CIAM (customer identity and access management) product, built on the same underlying authentication infrastructure as Firebase Authentication but positioned and licensed for enterprise CIAM use
- A patient login system built and hosted by the portal application itself

**Decision:** Google Cloud Identity Platform, as a distinct identity population from workforce Cloud Identity/Managed Microsoft AD.

**Rationale:**
Building and hosting patient login directly in the portal application means owning password storage, MFA, account recovery, and breach response for ~2 million patient identities — the identical undifferentiated-heavy-lifting objection ADR-009/ADR-016 raised, unchanged by platform. Extending the workforce directory to also hold patient accounts is worse, not better, for the same reason: it mixes a consumer population with materially different risk and lifecycle characteristics into the same directory that governs access to clinical systems, and every future workforce policy change now has to account for patient accounts it was never meant to affect. Identity Platform is purpose-built for exactly this split: native OIDC/SAML support the portal already needs, multi-tenancy, and — critically — a genuinely separate identity boundary from Cloud Identity/Managed Microsoft AD, the same structural separation Entra External ID gives Azure and Cognito User Pools gives AWS.

**Trade-off:**
This means the portal integrates against two identity providers instead of one — more configuration, two sets of policies to reason about, and two places an identity-related incident could originate, the identical trade-off ADR-009/ADR-016 accepted. A GCP-specific wrinkle worth naming: Identity Platform's risk-based/adaptive authentication and device-posture signals are, like AWS IAM Identity Center (ADR-016's own named gap), less mature than Microsoft Entra ID P2's Conditional Access and Identity Protection — there is no first-party GCP equivalent to "block sign-in from a non-compliant device" at the same depth. Closing that gap fully on GCP, as on AWS, realistically means a third-party identity/CASB layer (Okta, Duo) in front of or alongside Identity Platform, or accepting a weaker Conditional-Access-equivalent posture than the Azure design achieves natively. Flagged here for the same reason ADR-016 flagged it for AWS: the March 2026 credential-compromise incident is exactly the failure mode these controls exist to prevent, and this gap should carry real weight in the Step 10 decision matrix, not be treated as a rounding error.

**Status:** Proposed
