### ADR-025: GCP messaging platform for the Integration Bus (LinkEngine)

**Context:**
ADR-002 already decided the Integration Bus is event-driven, replacing LinkEngine's point-to-point HL7v2 feeds — platform-neutral. ADR-022 already decided what *processes* messages once they arrive (Cloud Run functions, one per category). Neither decided which GCP messaging service those functions actually subscribe to — that's what this ADR settles, mirroring ADR-011 for Azure and ADR-018 for AWS.

**Options considered:**
- Google Cloud Pub/Sub, using ordering keys for per-patient sequencing and dead-letter topics for failed messages
- Google Cloud Tasks — a managed task-queue service for asynchronous, app-triggered work
- Self-managed Apache Kafka on GKE, or a third-party managed Kafka offering on GCP Marketplace

**Decision:** Google Cloud Pub/Sub, one topic per message category, with an ordering key of patient ID and a dead-letter topic per subscription.

**Rationale:**
Cloud Tasks is built for a different problem — an application explicitly scheduling and dispatching its own discrete units of work to a known handler — not a publish/subscribe pattern where multiple, independent downstream consumers react to events they didn't request. It lacks Pub/Sub's fan-out and topic/subscription model entirely, the same category mismatch that ruled out simpler queue-only options for Azure and AWS. Self-managed Kafka is rejected for the identical reason ADR-011/ADR-018 rejected Event Hubs and MSK respectively: LinkEngine's actual requirement is reliable, ordered, retryable per-patient delivery, not high-volume log-based streaming, and Kafka has no native per-message dead-lettering — that reliability would have to be built on top of it, real engineering effort this design avoids by picking the tool built for the job. Pub/Sub is the only option of the three that combines native per-key ordering, native dead-lettering, and a fully serverless operational model with nothing to provision or manage ahead of time — direct parity with SNS FIFO/SQS FIFO's role on AWS and Service Bus sessions' role on Azure.

**A genuine simplification worth naming, not just a renamed service.** AWS's design needed two services working together — SNS for fan-out, SQS for the durable, pollable per-consumer queue — because SNS alone has no message retention or pull semantics of its own. GCP's Pub/Sub collapses both roles into one service: a **topic** provides the fan-out point, and each **subscription** on that topic is itself a durable, independently-acknowledged queue, with its own retry and dead-letter behavior. One topic with N subscriptions does the job SNS+SQS needed two distinct services to do — a real architectural simplification, not just fewer boxes on a diagram, and worth weighing as a genuine point in Pub/Sub's favor for the Step 10 comparison.

**Trade-off:**
Cloud Tasks would have been simpler to reason about if LinkEngine only ever needed one consumer per message type, and a managed Kafka offering would give more throughput headroom and broader ecosystem tooling than this workload needs — but both trade real capability (Pub/Sub's ordering/dead-lettering) for something this design doesn't require. A GCP-specific nuance worth stating precisely, not glossed over: Pub/Sub's ordering keys guarantee delivery order *within* a key to a given subscriber, and its "exactly-once delivery" subscription setting prevents duplicate delivery to that subscription — but this is a different mechanism from SQS FIFO's content-based deduplication (which prevents publishing near-duplicate messages in the first place). Producer-side duplicate suppression, if ever needed, would have to be handled by the Publish Function itself (see Proposed Configuration below), not assumed to come from the messaging layer the way SQS FIFO's content hashing provides it.

**Status:** Proposed

**Proposed Configuration:**

| Setting | Proposed value | Rationale |
| --- | --- | --- |
| Pattern | Apigee-fronted Cloud Run function (`linkengine-publish-function`) → Pub/Sub topic → per-category Pub/Sub subscription (one Cloud Run function subscriber per topic, ADR-022) | Direct structural parity with ADR-018's Publish-Function-to-SNS-to-SQS pattern — the Publish Function parses each inbound HL7v2 message and routes it to the right topic; Pub/Sub provides both the fan-out point and the durable per-subscriber queue (see Rationale above) |
| Publish/ingest compute | Cloud Run function (`linkengine-publish-function`), invoked via Apigee's backend target after mTLS/quota validation. Max instances 10, min instances 1. Direct VPC egress into `subnet-integration`, the dedicated Integration VPC (10.50.0.0/16) — shared with the four subscriber functions, not the Portal (ADR-022). IAM scoped to the Pub/Sub Publisher role on the 4 topics only | Apigee's policy engine, like Amazon API Gateway's mapping templates, operates on JSON/XML transforms and can't reliably extract a patient ID from raw pipe-delimited HL7v2 text — the identical real constraint ADR-018 named for AWS, still true here because it's a property of the message format, not the platform. A small parsing/routing function is genuinely necessary, not just convenient. Sharing `subnet-integration` (rather than a dedicated subnet of its own) is safe on IP-capacity grounds for the reason ADR-022 already established: Cloud Run's Direct VPC egress doesn't consume one IP per concurrent execution the way AWS Lambda's ENI model does. Placing it in the Integration VPC rather than alongside the Portal is a separate, deliberate choice — this function is the one entry point in the platform reached by externally-triggered partner traffic (via Apigee), not a Meridian-authenticated user or staff member, the same trust-boundary reasoning ADR-022 applies to the four subscriber functions |
| API ingress | Apigee (not GCP's lighter-weight Cloud API Gateway product) | Apigee is chosen as the platform's API management layer specifically for feature parity with Azure APIM Premium and Amazon API Gateway's usage-plan model — mTLS client-certificate validation and per-partner quota/rate-limiting — depth that GCP's lighter Cloud API Gateway product doesn't offer at the same level. See `gcp-implementation.md` §1 for the platform-wide API ingress decision this reuses |
| Topics/Subscriptions | 4 topics (lab results, imaging, e-prescribing, appointment events), one subscription per topic | Direct parity with ADR-011/ADR-018's 4 topics — reused unchanged from `application-architecture.md`'s per-category message model |
| Ordering | Ordering key = patient ID, per subscription | Direct parity with Service Bus sessions (ADR-011) and SNS/SQS FIFO's `MessageGroupId` (ADR-018) — keeps multiple messages for the same patient processed in order |
| Duplicate handling | Exactly-once delivery enabled per subscription | Prevents the same message from being delivered more than once to a given subscription — see the Trade-off section for how this differs from SQS FIFO's content-based deduplication |
| Dead-letter handling | Dead-letter topic per subscription, `max delivery attempts = 10`, Cloud Monitoring alert on dead-letter topic depth | Direct parity with ADR-011/ADR-018's "10 attempts before dead-letter" |
| Message size | Up to 10 MB (Pub/Sub's per-message limit) | HL7v2 text messages are a few KB each — comfortably within limit, no extension mechanism needed. Large binary content (imaging) doesn't travel through the bus — archived to Cloud Storage directly, mirroring ADR-011/ADR-018's approach |
| Zone/region redundancy | Regional Pub/Sub topic (multi-zone within the region by default) | A genuine simplification versus both sibling platforms, the same category of simplification ADR-018 named for SNS/SQS versus Service Bus Premium's explicit AZ-enablement step: Pub/Sub's zone redundancy isn't a tier or configuration decision at all, it's inherent to the service |
| DR | See the gap below — no native cross-region topic replication | Like SNS/SQS, Pub/Sub topics and subscriptions are regional resources with no built-in cross-region replication feature |

**Where the throughput comfort margin comes from.** `current-state.md`'s ~1.1M HL7 messages/month, ~0.42 messages/second sustained, roughly 5-10 messages/second at planning-assumption peak — the identical figures reused unchanged across every platform's messaging ADR, since message volume doesn't depend on which cloud processes it. Pub/Sub's per-topic throughput ceiling is, like SQS FIFO and Service Bus Premium, orders of magnitude above this workload, so there's no unit-sizing decision to make here either.

**A gap worth surfacing, not glossing over.** Like Amazon SNS/SQS (ADR-018's own flagged gap), Google Cloud Pub/Sub has **no native cross-region replication or failover feature** — topics and subscriptions are regional resources. The DR approach mirrors ADR-018's exactly: (1) provision matching Pub/Sub topics and subscriptions in `us-west1` via the same IaC used for `us-central1`, kept in sync as pure infrastructure with no message content involved, and (2) on failover, rely on the identical source-system reconciliation strategy ADR-011/ADR-018 already established — LabCorp, Quest, and Surescripts all support querying for results/messages already sent. This should be added explicitly to the GCP DR runbook (see `gcp-implementation.md` §12) exactly as the Azure and AWS equivalents were. Cost for this configuration is deliberately not estimated here and stays with Step 13.
