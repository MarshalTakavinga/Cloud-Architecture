### ADR-028: Private-cloud database service for the primary relational database

**Context:**
ADR-003 already decided the data layer stays managed relational, not NoSQL — platform-neutral. Every sibling ADR (ADR-006 for Azure, ADR-013 for AWS, ADR-020 for GCP) answered "which managed relational tier" from a real menu of managed-service options with different compatibility ceilings. This ADR does not have that menu, and that absence is the entire substance of this decision, not a footnote to it.

**Options considered:**
- Self-managed SQL Server 2022 Enterprise on VCF-managed vSphere VMs, using SQL Server's own Always On Availability Group feature for HA and cross-facility DR
- SQL Server on VCF-managed vSphere VMs, relying on vSAN/vSphere HA and Site Recovery Manager-style replication instead of a database-native Availability Group
- A Kubernetes-operator-managed SQL deployment on the Tanzu platform (ADR-030)

**Decision:** Self-managed SQL Server 2022 Enterprise, deployed on VCF-managed vSphere VMs, using a native SQL Server Always On Availability Group: a synchronous replica within the primary facility's Production VI Workload Domain, and an asynchronous replica in the DR facility.

**Rationale:**
**This is the sharpest, most consequential difference between the private-cloud track and its three siblings, and it deserves to be stated plainly rather than discovered later in a trade-off paragraph.** There is no managed-database tier in private cloud — no Cloud SQL, no RDS of any kind, no Azure SQL Managed Instance. VCF and vSAN provide software-defined compute and storage resilience underneath a VM, but neither provides database-level automated failover orchestration, engine patching, or backup automation the way a managed service does. Every one of ADR-006, ADR-013, and ADR-020 was fundamentally a choice between tiers of an already-managed product; this ADR has no such tier to choose from. The realistic options are therefore genuinely different in kind, not just degree: rely on infrastructure-level resilience (vSphere HA restarting a failed VM, vSAN protecting the underlying storage) and accept the outage-and-recovery window that implies, or build the same Always On Availability Group technology already running today (`current-state.md`) — this time actually deployed correctly, across two physical facilities instead of two nodes in the same room. Infrastructure-level HA alone (the second option) is rejected because it cannot hit the ≤ 4 hour RTO / ≤ 15 minute RPO requirement (`requirements.md`) on its own — a VM restart after a host failure is not a database failover, and it does nothing at all for a full facility loss. A Kubernetes-operator-managed SQL deployment on Tanzu is rejected for the same compatibility reason ADR-020 raised about Cloud SQL's ceiling, self-inflicted here for no benefit: CareLink PM's vendor support matrix, and SQL Server's own certification story, assume a conventional Windows Server host — containerizing the database of a legacy vendor thick-client application is a real compatibility risk with no corresponding upside when a conventional VM option is safely available.

**Trade-off:**
This is the single largest, most consequential trade-off named anywhere in this track, and it should carry real weight in Step 10, not be treated as a rounding difference in vendor names. Choosing private cloud for the database tier means **keeping**, not eliminating, exactly the operational burden — OS patching, SQL Server patching, Availability Group configuration and monitoring, failover testing, backup job design and testing — that ADR-001 and ADR-003 identified as a core problem with the current state, and that every hyperscaler database ADR (ADR-006, ADR-013, ADR-020) was chosen specifically to remove. It falls squarely on Meridian's 4 DBAs/application admins (`current-state.md` §1 staffing), the same team currently carrying this burden today, unsupported, against an out-of-extended-support engine. The genuine improvement here is real but narrower than it might first appear: correctly separating the two Availability Group replicas across physically independent facilities (rather than the current state's two replicas in the same building) closes the actual root-cause gap that made the current DR posture fictional — but it does not remove the ongoing patching and operational burden the way a managed tier would.

**Status:** Proposed

**Proposed Configuration:**

| Setting | Proposed value | Rationale |
| --- | --- | --- |
| Engine / edition | SQL Server 2022 Enterprise | Enterprise edition is required for Always On Availability Groups with more than a basic two-node configuration and for the encryption/auditing features this design needs — a direct, licensed cost this design accepts explicitly, unlike a managed tier's bundled licensing |
| Primary facility topology | 2 VMs in a synchronous Always On Availability Group, spread across separate ESXi hosts via DRS anti-affinity (ADR-027) | Direct parity with ADR-006's Zone Redundant tier and ADR-013/ADR-020's Multi-AZ/Regional-HA configurations — the closest private-cloud equivalent of "synchronous replica in a second failure domain within the region" |
| DR facility topology | 1 VM, asynchronous Always On replica, pre-provisioned at full target capacity per ADR-026 | Implements ADR-004's warm-standby design — asynchronous because synchronous commit across a Columbus–Dallas WAN link would add unacceptable transaction latency to a clinical scheduling workload |
| VM spec | 16 vCPU / 128 GB per replica (starting point) | Directional sizing parity with ADR-006/ADR-013/ADR-020's 8-vCore starting points, sized up modestly to account for this design carrying its own OS/engine overhead without a managed control plane absorbing any of it — provisional pending real telemetry from the current on-prem SQL Server 2014 nodes, which was never captured per-VM |
| Storage | vSAN, capacity-tier storage policy (FTT=2, RAID-1 mirroring) for the database VMs' disks specifically | A stronger vSAN protection level than the Citrix session-host tier (ADR-027's FTT=1) because this is stateful, not disposable, data — FTT=2 tolerates two concurrent host/disk failures before data loss, layered underneath (not a replacement for) the Availability Group's own replica-level protection |
| Backup | Veeam Backup & Replication (continuing the product already in use today, `current-state.md` §3), with an immutable, hardened-repository target and cross-facility replication of backup data to the DR facility | Directly closes the "immutable, geographically separate backup" requirement (`requirements.md`) and the ransomware-resilience gap the current same-SAN Veeam target cannot provide — this is also the one component in the entire private-cloud track that most directly upgrades, rather than replaces, tooling Meridian's team already operates, worth naming as a genuine continuity strength of this track |
| Encryption | Transparent Data Encryption (TDE) at rest, keys managed via a dedicated key-management service (not co-located with the database VMs) | Matches the "no exceptions carried forward from unencrypted legacy LUNs" requirement; a dedicated key-management tier (rather than storing keys alongside the data they protect) is the private-cloud analog to the CMEK/Cloud KMS pattern used in ADR-020 |
| Cross-region DR replication | SQL Server Always On asynchronous replica, promoted manually per the DR runbook | See `docs/private-cloud-implementation.md` §8/§12 for the full runbook — this is a database-native mechanism Meridian operates directly, not a managed cross-region replica feature the platform provides for it |

Cost for this configuration — including SQL Server Enterprise licensing (a real, material cost at this VM count that the managed-tier comparisons on the other three platforms bundle differently), storage, and backup infrastructure — is deliberately not estimated here and stays with Step 13.
