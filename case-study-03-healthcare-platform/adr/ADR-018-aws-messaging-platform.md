### ADR-018: AWS messaging platform for the Integration Bus (LinkEngine)

**Context:**
ADR-002 already decided the Integration Bus is event-driven, replacing LinkEngine's point-to-point HL7v2 feeds — platform-neutral. ADR-015 already decided what *processes* messages once they arrive (AWS Lambda, one function per topic/queue). Neither decided which AWS messaging service those Lambda functions actually subscribe to — that's what this ADR settles, mirroring ADR-011 for Azure.

**Options considered:**
- Amazon SNS (FIFO topics) fanning out to Amazon SQS (FIFO queues) per subscriber — brokered pub/sub with per-message-group ordering and dead-letter queues
- Amazon MQ (managed ActiveMQ/RabbitMQ) — broker instances with message-group/JMS-style ordering semantics
- Amazon MSK (managed Apache Kafka) — high-throughput, log-based event streaming/ingestion

**Decision:** Amazon SNS FIFO topics fanning out to Amazon SQS FIFO subscriber queues, using `MessageGroupId` = patient ID.

**Rationale:**
LinkEngine's actual requirement is reliable, ordered, retryable delivery of HL7v2 messages per patient — not high-volume telemetry ingestion and not simple discrete-event fan-out, the identical framing ADR-011 used for Azure. Amazon MSK is built for millions of events per second in an append-only log (IoT telemetry, clickstreams); it has no native per-message dead-lettering or lock-and-complete semantics, so HL7-grade reliability would have to be built on top of it — the same objection ADR-011 raised against Azure Event Hubs. Amazon MQ provides message-group ordering, but it requires provisioning and operating broker instances directly (instance sizing, patching, HA configuration) — real infrastructure to manage, unlike SNS/SQS's fully serverless, no-servers-to-size model, and a materially different operational shape than the managed-broker experience Service Bus Premium gave the Azure design. SNS FIFO + SQS FIFO is the only one of the three that combines native per-message-group ordering (`MessageGroupId`, keeping every message for the same patient in order — direct parity with Service Bus sessions), native dead-letter queues via redrive policy, and a fully serverless operational model with no capacity units to provision ahead of time.

**Trade-off:**
Amazon MSK would handle far higher raw throughput than this workload needs, and Amazon MQ gives more protocol flexibility (native JMS/AMQP/MQTT support) if Meridian ever needs to integrate a legacy system that only speaks one of those protocols — but both require real engineering effort or infrastructure this design avoids by picking the tool built for the job, the same trade-off ADR-011 accepted. A second, AWS-specific point worth naming directly: unlike Service Bus Premium's Messaging Unit model, SNS/SQS FIFO has **no pre-provisioned throughput unit to size at all** — it's consumption-priced, and SQS FIFO's per-API-action throughput ceiling (up to 300 transactions/second per API action without batching, far higher with batching, and materially higher still using high-throughput mode for FIFO queues introduced in recent SQS updates) comfortably exceeds anything this workload will produce. This is a genuine simplification versus the Azure design, not a wash — there's no MU-equivalent capacity-planning exercise required here, and it's called out honestly as an AWS advantage in this specific comparison rather than skipped over.

**Status:** Proposed

**Proposed Configuration:**

| Setting | Proposed value | Rationale |
| --- | --- | --- |
| Pattern | AWS Lambda Publish Function → SNS FIFO topic → SQS FIFO queue (one queue per topic, one Lambda subscriber per queue) | Decided above — the Publish Function parses each inbound HL7v2 message and routes it to the right topic; SNS provides the pub/sub fan-out point (useful if a second consumer is ever added to a topic later without changing the producer), SQS provides the durable, pollable queue Lambda's event source mapping actually consumes from |
| Publish/ingest compute | AWS Lambda (`linkengine-publish-function`), invoked via API Gateway's Lambda proxy integration after mTLS/rate-limit validation. Reserved concurrency 10, provisioned concurrency 1. VPC-attached in `subnet-lambda-linkengine-az1/az2/az3` alongside the four subscriber functions (ADR-015). IAM execution role scoped to `sns:Publish` on the 4 topics only | API Gateway's mapping templates operate on JSON/XML and can't reliably extract a patient ID from raw pipe-delimited HL7v2 text, so a direct API Gateway-to-SNS service integration (no compute in between) isn't viable here the way it might be for a JSON payload — a small parsing/routing Lambda is genuinely necessary, not just convenient. Sharing the existing LinkEngine Lambda subnets (rather than provisioning new ones) keeps this consistent with ADR-015's subnet, since it's still LinkEngine compute; reaches SNS over the same VPC interface endpoint the subscriber functions already use, keeping the private-path posture consistent. Reserved concurrency of 10 (lower than each subscriber's 20) reflects that this single function absorbs the combined inbound rate across all 4 categories, not one category's backlog; provisioned concurrency of 1 avoids cold-start latency on the external-facing ingest path for the same reason ADR-015 keeps subscribers warm |
| Topics/Queues | 4 — lab results, imaging, e-prescribing, appointment events | Direct parity with ADR-011's 4 topics — already established in `application-architecture.md`'s per-category message model, reused unchanged since the message taxonomy is platform-independent |
| Ordering | FIFO topic and queue, `MessageGroupId` = patient ID | Direct parity with Service Bus sessions (ADR-011) — keeps multiple messages for the same patient processed in order, the exact mechanism `application-architecture-aws.md` documents for the Publish Function's HL7v2 parsing step |
| Deduplication | Content-based deduplication enabled (SHA-256 of message body) | SQS FIFO requires either an explicit `MessageDeduplicationId` or content-based deduplication; content-based is used here since HL7 messages carry a natural uniqueness in their content and no separate producer-side ID scheme exists yet to generate one deliberately |
| Dead-letter handling | Redrive policy per queue, `maxReceiveCount = 10`, dedicated DLQ per topic + CloudWatch alarm on DLQ depth | Direct parity with ADR-011's "10 attempts before dead-letter" — high enough to absorb a transient downstream fault (e.g., the database briefly unavailable during a failover), low enough that a genuinely bad message (unmatched patient ID) reaches the DLQ and an on-call alert within a reasonable window |
| Message size | Up to 256 KB (SQS default, no Extended Client Library needed) | HL7v2 text messages are a few KB each — comfortably within the default limit, no need for the S3-backed large-message extension. Large binary content (imaging) doesn't travel through the bus at all — archived to S3 directly, mirroring ADR-011's Blob Storage approach |
| Availability Zones | Multi-AZ by default (SNS/SQS are regional, zone-redundant services with no configuration required) | A genuine simplification versus Service Bus, which required explicitly enabling Availability Zones on the Premium tier — SNS/SQS zone redundancy isn't a tier decision to make, it's inherent to the service |
| DR | See the gap below — no native cross-region pairing | Unlike Service Bus Premium's Geo-Disaster Recovery, SNS/SQS have no built-in cross-region replication feature at all |

**Where the throughput comfort margin comes from.** `current-state.md` captures LinkEngine's actual current volume: ~1.1M HL7 messages/month, ~0.42 messages/second sustained, with a planning-assumption peak (10-20x burst multiplier for a batch lab-result delivery window) of roughly 5-10 messages/second — the identical figures ADR-011 used, reused unchanged here since message volume doesn't depend on which cloud platform processes it. SQS FIFO's throughput ceiling is orders of magnitude above this even in its default (non-high-throughput) mode, so unlike ADR-011 there's no unit-sizing decision to make here at all — see the Trade-off section above.

**A gap worth surfacing, not glossing over — and a bigger one than Azure's.** Amazon SNS and SQS are both fully regional services with **no native cross-region replication or failover feature**, unlike Azure Service Bus Premium's Geo-Disaster Recovery, which at minimum auto-replicates namespace topology (queues, topics, subscriptions, rules) even though it doesn't replicate in-flight message content (ADR-011's own documented gap). On AWS, *nothing* is automatically replicated — not even topology. The DR approach here is: (1) provision matching SNS topics and SQS FIFO queues in us-west-2 via the same IaC templates used for us-east-1, kept in sync as pure infrastructure (no message replication involved), and (2) on failover, rely on the identical source-system reconciliation strategy ADR-011 already established for Azure — LabCorp, Quest, and Surescripts all support querying for results/messages already sent, since an interface engine losing a feed mid-transit is a known, already-handled failure mode for these partners. This should be added explicitly to the AWS DR runbook (see `aws-implementation.md` §12) exactly as ADR-011's equivalent gap was added to the Azure runbook — flagged here rather than left silently implied, and flagged as a materially larger gap than the Azure equivalent so it gets appropriate weight in the eventual decision matrix (Step 10). Cost for this configuration is deliberately not estimated here and stays with Step 13.
