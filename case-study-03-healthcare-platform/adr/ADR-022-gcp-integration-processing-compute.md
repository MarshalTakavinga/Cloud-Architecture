### ADR-022: Compute for LinkEngine's message-subscriber logic on GCP

**Context:**
ADR-002 decided LinkEngine becomes an event-driven integration service — platform-neutral. Something still has to run the code that subscribes to each message queue, writes results into the primary database, and archives the raw payload to object storage. The Compute Engine instances hosting CareLink PM (ADR-019) are a candidate simply because they already exist and are already connected to the data VPC — the same starting question ADR-008 answered for Azure and ADR-015 answered for AWS.

**Options considered:**
- Run the subscriber logic on the existing Citrix/CareLink PM Compute Engine tier, as a background Windows service
- Cloud Run functions (2nd generation — Google's current branding for what was Cloud Functions, built on Cloud Run's execution environment), VPC-connected, one function per message category
- Google Kubernetes Engine (GKE), running a small subscriber container/service

**Decision:** Cloud Run functions, one function per topic subscription.

**Rationale:**
The Citrix Compute Engine tier is sized and autoscaled around interactive clinical session load; message-processing load follows a completely different pattern — the identical reasoning ADR-008/ADR-015 used to reject the equivalent compute tier on their platforms. GKE is ruled out for the same staffing reason ADR-002 already ruled out full microservices generally: a 16-person infrastructure team with no current Kubernetes operating experience shouldn't take on cluster operations for a handful of short-lived, event-triggered functions. Cloud Run functions is chosen over both because it has first-class, native Eventarc/Pub/Sub triggers (Pub/Sub is the messaging platform chosen in ADR-025) and the workload here — genuinely event-driven, short-lived processing per message — is exactly Cloud Run functions' design point, mirroring ADR-008's choice of Azure Functions over Container Apps and ADR-015's choice of Lambda over Fargate for the same reason: native trigger integration over general-purpose container hosting.

**Trade-off:**
This adds a third distinct compute platform to the GCP environment (Compute Engine for Citrix, Cloud Run for the Portal, Cloud Run functions for LinkEngine), the same real operational cost ADR-008/ADR-015 named for their platforms. Accepted because the alternative — background processing on interactive session hosts — risks clinical-facing performance during exactly the periods (a message backlog after an outage) when reliability matters most.

**A separate placement decision worth stating explicitly, not just inherited from the compute choice above.** Choosing Cloud Run functions decides *what runs* the subscriber logic; it doesn't by itself decide *which VPC* those functions sit in. An earlier version of this design put LinkEngine's functions in the same VPC as the Portal and Citrix tiers, reasoning that Cloud Run's Direct VPC egress doesn't have AWS Lambda's per-execution IP-consumption problem, so there was no *capacity* reason to isolate them — that reasoning is still true, but it answered the wrong question. IP capacity isn't the only reason to isolate a compute tier: LinkEngine's Publish Function is the one compute tier in this entire platform invoked by traffic Meridian doesn't authenticate as a user or a member of staff — it's triggered by external partner systems (LabCorp, Quest, hospital PACS feeds, Surescripts) presenting a client certificate or API key through Apigee, not a Meridian identity. That's a materially different trust boundary from the Portal (Meridian-authenticated patients/staff) and Citrix (Meridian-authenticated staff only) sharing a subnet in the Application VPC. **Decision, restated:** LinkEngine's Cloud Run functions run in a dedicated **Integration VPC**, separate from the Application VPC, for network/IAM blast-radius isolation of the platform's externally-triggered ingest path — not for IP capacity, which was never the real constraint on GCP. See `gcp-implementation.md` §4/§4.1 for the addressing detail.

**Status:** Proposed

---

**Proposed Configuration:**

| Setting | Proposed value | Rationale |
| --- | --- | --- |
| Function structure | 4 Cloud Run functions (lab results, imaging, e-prescribing, appointment events), one per Pub/Sub subscription | Direct parity with ADR-008's "one function app per topic" and ADR-015's "one Lambda per queue" — each function scales independently on its own subscription's backlog |
| Trigger | Pub/Sub push subscription (Eventarc), one message at a time | Because the underlying Pub/Sub topics use an ordering key = patient ID (ADR-025) to preserve per-patient order, delivery is kept single-message-at-a-time so ordering isn't broken by concurrent processing within the same key |
| Memory / timeout | 512 MiB, 30 second timeout (starting point) | The subscriber workload is I/O-bound, not compute-bound — parse an HL7 message, write to the database, archive to Cloud Storage, acknowledge the message — mirroring ADR-008/ADR-015's reasoning. Revisit if real usage shows CPU/memory pressure |
| Concurrency / scaling | Max instances 20 per function (starting ceiling), min instances 1 | Direct parity with ADR-008's 20-instance burst ceiling and ADR-015's reserved-concurrency-20 figure — headroom for a backlog-catch-up scenario. Min instances 1 keeps one instance warm per function, avoiding cold-start latency on clinically time-sensitive categories (lab results, e-prescribing) — the GCP analog to ADR-015's provisioned-concurrency-1 setting |
| VPC integration | Direct VPC egress into `subnet-integration`, a dedicated **Integration VPC** (10.50.0.0/16) — separate from the Application VPC that hosts Apigee's runtime, the Portal's Cloud Run service, and Citrix (see `gcp-implementation.md` §4.1) | **Two genuine platform points worth separating, not conflating.** First, a genuine simplification versus AWS: ADR-015 isolated AWS Lambda's LinkEngine functions into their own dedicated subnets specifically because each concurrent Lambda execution consumes an IP address for the duration of its VPC-attached ENI, risking IP exhaustion under a burst; Cloud Run's Direct VPC egress has no equivalent per-execution IP cost, so that specific AWS constraint doesn't transfer. Second, and separately: isolation is still the right call here, but for a network/IAM blast-radius reason, not a capacity one — see this ADR's Trade-off section for why LinkEngine's externally-triggered ingest path is a different trust boundary from the Application VPC's Meridian-authenticated traffic. The two points don't cancel out: the *why* changed, the *isolate it* conclusion didn't |
| Identity | A dedicated service account per function, least-privilege (Pub/Sub subscriber role scoped to its own subscription + dead-letter topic, Cloud SQL Client role, Cloud Storage object-write role scoped to its own archive prefix) | Same least-privilege discipline as ADR-008's managed identity per function app and ADR-015's per-function IAM execution role — no shared, over-privileged identity across all four functions |

This sizing is a directional starting point, same discipline as ADR-019/ADR-020/ADR-024/ADR-025: there's no per-message-processing telemetry from the current on-prem LinkEngine to validate concurrency assumptions against, only the message-volume figures already used across every platform's messaging ADR. Validate against real Cloud Monitoring/Cloud Trace data after cutover. Cost for this configuration is deliberately not estimated here and stays with Step 13.
