# ADR-011: AWS Compute Platform for the New Real-Time Services and the Nightly Reconciliation Job

**Status:** Approved
**Date:** Step 7 of the Case Study 2 pipeline

## Context

[Step 5](../docs/logical-design.md) defined three new, greenfield services that need a compute platform on AWS: the Hold/Release Adapter, the Fraud Orchestration Service, and the Ledger-of-Intent Service (application tier). All three are stateless request/event handlers, share the same deployment cadence, and carry the same latency-sensitive constraints — NFR-4 requires fraud-scoring decisions in ≤300ms, and NFR-3 requires end-to-end posting latency ≤5 seconds. `requirements.md` also flags a cloud-skills gap at Palisade: this is a bank whose engineering organization has run a mainframe and a vendor-licensed digital banking platform, not a Kubernetes estate. A fourth new-build component, the nightly **Reconciliation Process** ([ADR-003](ADR-003-provisional-vs-confirmed-state-model.md)), has a very different execution profile — it runs once a day, not continuously — and needs its own answer within the same decision.

## Decision

The three always-on, latency-sensitive services run on **AWS Fargate on Amazon ECS**, each as its own ECS Service within the same ECS cluster (Fargate launch type only — no EC2 instances to patch or scale), with a minimum task count of 2 per service to avoid cold-start latency on the fraud-scoring and hold/release paths, and Application Auto Scaling target-tracking policies following payment-volume variability. The nightly **Reconciliation Process** runs as a scheduled **Fargate task**, launched by **Amazon EventBridge Scheduler** on a nightly cron rule via an ECS `RunTask` invocation, in the same cluster as the three always-on services — not as a fourth ECS Service, and not on a second compute platform.

## Alternatives Considered (rejected, retained here rather than deleted)

1. **Amazon EKS.** Rejected — EKS gives more low-level control than this workload needs (three uniform, stateless services, not a large heterogeneous microservices estate), and its cluster control-plane and node-group management overhead falls directly on a team `requirements.md` already flags as short on cloud-native skills. Same reasoning [ADR-005](ADR-005-azure-compute-platform.md) used to reject AKS for the Azure track.
2. **AWS Lambda for the three real-time services.** Rejected as the *primary* platform for the fraud-scoring path specifically — even with Provisioned Concurrency, Lambda's per-invocation execution model is a weaker fit than a long-lived, always-warm service for a component that needs to fit inside NFR-4's 300ms budget on every call, and the Ledger-of-Intent Service's application tier benefits from a persistent connection pool to Aurora that a long-lived container manages more naturally than a function invocation. Lambda remains a candidate for genuinely bursty, non-latency-critical peripheral work, but that is a Step 13 sizing detail, not a Step 7 architectural decision — the same carve-out [ADR-005](ADR-005-azure-compute-platform.md) made for Azure Functions.
3. **AWS App Runner.** Considered — App Runner is a simpler, fully managed container service than ECS/Fargate, with even less to configure. Rejected narrowly: App Runner's private outbound networking (VPC Connector) is a bolt-on rather than the native, first-class VPC-subnet attachment ECS/Fargate tasks get by default, and this workload's most compliance-sensitive property — the private, non-internet-traversing path for the synchronous CICS hold call and for Aurora access — is better served by a compute platform where VPC-native networking is the default, not an add-on. Fargate also has broader precedent in regulated-workload reference architectures than the newer App Runner service.
4. **A fourth always-on ECS Service for the Reconciliation Process**, mirroring the other three. Rejected — the Reconciliation Process runs once nightly, after the batch window closes; keeping tasks running continuously for a job that fires once a day is unnecessary cost and operational surface with no latency benefit, since neither NFR-3 nor NFR-4 applies to a process that isn't customer-facing.
5. **AWS Batch for the Reconciliation Process specifically.** Considered — AWS Batch is a legitimate fit for a scheduled batch job on its own merits. Rejected only narrowly, in favor of keeping every new-build compute workload on one platform (Fargate) rather than introducing a second compute service for a single job — the same "one consistent compute model" reasoning [ADR-005](ADR-005-azure-compute-platform.md) used to reject a separate Azure Functions timer trigger for the equivalent job.

## Consequences

- **Positive:** One consistent compute model across all four new-build components — the three always-on services and the nightly job — simplifies operations, observability, and the team's learning curve, directly responsive to the cloud-skills-gap constraint.
- **Positive:** Application Auto Scaling on the always-on services means capacity follows real-time-payment volume without a human resizing anything, consistent with driver 3 (flattening the cost trajectory) — idle capacity is not paid for at 3am when FedNow volume is low. The Reconciliation task takes this further: it costs nothing to run at all outside its nightly trigger window.
- **Negative / accepted trade-off:** Fargate offers less low-level infrastructure control than EKS would (e.g., custom CNI, node-level tuning). Accepted because none of the four components need that control today; if a future capability genuinely requires it, that is a new decision to revisit, not a gap in this one.
- **Note for Steps 8–9:** AWS's ECS has no first-class "job" resource type the way Azure Container Apps Jobs is — the equivalent here is a scheduled `RunTask` invocation, a real, structural difference in how the same nightly-job problem is solved, worth carrying into Step 10's platform comparison.
- **Carried to Step 13:** Exact task counts, CPU/memory allocation, and scaling thresholds, along with the Reconciliation task's EventBridge Scheduler cron expression and timeout settings, are a cost-and-sizing exercise, deferred to Step 13 by this case study's convention.
