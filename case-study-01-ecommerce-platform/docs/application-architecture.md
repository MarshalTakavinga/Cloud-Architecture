# Per-Service Implementation Architecture — Solstice Retail Group on Azure

`azure-implementation.md` maps every logical component to an Azure service. This document goes one level deeper: for each owned service, it answers what compute it runs on and how many instances, exactly how it reaches its data, whether it's public or private and who can reach it, and how it scales and survives a failure. Four owned services are covered — Storefront & Catalog, Cart, Checkout & Payment, and Inventory & Order Orchestration — plus the Global Catalog data tier they share.

## 1. Storefront & Catalog Service

**Migration strategy:** Rearchitect (ADR-001). **Compute:** Azure Container Apps, Consumption + Dedicated mixed profile, one environment per active region, shared with Cart (ADR-005). **Data:** reads from that region's Global Catalog read replica (ADR-007) — never the US primary directly, even for US-region traffic, since keeping every region's read path uniform (replica-only) avoids a special-cased "US reads from primary, everyone else reads from a replica" branch in the code.

**Hosting architecture.** Each region's Storefront & Catalog container app is stateless by design — the in-memory catalog cache that made SCE's current cold start 3–4 minutes long (`current-state.md` §2) is removed entirely from the request path. In its place: Azure Cache for Redis, one instance per region, sits between the service and its PostgreSQL replica as a read-through cache for the highest-traffic product and category pages. A cache miss reads from the regional PostgreSQL replica over a private endpoint; a cache hit never touches the database at all. Product search queries route to that region's Azure AI Search index, kept current via a change feed from the regional Global Catalog replica rather than a direct write path from the service itself.

**Public or private, and how customers reach it.** Nothing in this service's subnet (`snet-storefront-cart`) has a public IP. Customers reach Azure Front Door (Section 7 of `azure-implementation.md`) over the public internet; Front Door routes to the nearest active region's API Management instance, which routes over the private VNet connection to the Container Apps environment. No direct public path to the service exists.

**Scaling and HA.** KEDA's HTTP-concurrency scaler targets roughly 40 concurrent requests per replica, scaling from a 4-replica regional floor up to roughly 80 replicas during a named 25x peak event (ADR-005's Proposed Configuration). Because the service holds no local session or cache state that would be lost on replica churn, scaling out is just adding capacity — there's no warm-up penalty the way there was with SCE's in-memory catalog cache. Availability Zone spread within the region (Container Apps' Consumption plan is zone-redundant by default) handles a single-zone failure; Front Door's latency-based routing away from an unhealthy region handles the rest, per `azure-implementation.md` §11.

## 2. Cart Service

**Migration strategy:** Refactor (ADR-001) — extracted into its own service, same inherently synchronous request/response interaction pattern, not rebuilt event-driven. **Compute:** same Container Apps environment as Storefront & Catalog (ADR-005). **Data:** session-scoped cart state lives in Azure Cache for Redis (the same regional Redis instance Storefront & Catalog uses for its read-through cache, a separate logical database within it) for active sessions, with a periodic write-behind to that region's Regional Transactional Store (ADR-006) so an abandoned-but-not-expired cart survives a Redis instance restart.

**Public or private, and how customers reach it.** Same path as Storefront & Catalog — Front Door → regional API Management → private VNet connection into `snet-storefront-cart`. No public IP on the Cart service itself.

**Scaling and HA.** Scales on the same HTTP-concurrency trigger as Storefront & Catalog, independently — a cart-heavy traffic pattern (many add-to-cart actions, few page views) scales Cart without over-provisioning Storefront & Catalog, and vice versa, since each container app inside the shared environment scales on its own replica count even though they share the environment's compute pool. Redis Standard tier's built-in replica handles a primary-node failure within the region; regional-primary partitioning (ADR-003, ADR-006) means a full regional outage loses write availability for that region's in-flight carts until the region recovers, an already-accepted trade-off, not a new one introduced at this layer.

## 3. Checkout & Payment Service

**Migration strategy:** Rearchitect (ADR-001) — the PCI-scope-driven rebuild. **Compute:** a **separate, dedicated** Azure Container Apps environment per active region, its own subnet (`snet-checkout`), its own network security group (ADR-005). **Data:** writes to that region's Regional Transactional Store (ADR-006), same PostgreSQL server Cart and Order data live in, different tables.

**Hosting architecture.** This is the one service in the whole design where the network boundary matters as much as the code. ADR-004 already decided the mechanism that keeps raw cardholder data out of this service entirely — the customer's browser sends card data straight to the Payment Gateway via hosted fields, and Checkout & Payment only ever receives a payment token back. What this service's own dedicated environment and subnet add on top of that is defense in depth: even though Checkout & Payment never touches raw card data by design, giving it its own network segment means everything else that *does* run here (order-capture logic, the payment token itself, the call to the gateway to charge that token) sits inside a narrower, independently-controlled network boundary than the general storefront traffic, which is the concrete meaning of ADR-001/ADR-002's "isolated network segment."

**Public or private, and how customers reach it.** Same Front Door → regional API Management path as every other customer-facing service — API Management is the only ingress `snet-checkout` accepts traffic from; the NSG on `snet-checkout` denies inbound traffic from `snet-storefront-cart` and every other subnet in the same spoke, not just from the public internet.

**Scaling and HA.** A smaller floor and ceiling than Storefront & Catalog (2 to ~30 replicas per region, ADR-005's Proposed Configuration) — checkout traffic volume is a fraction of browse traffic even during a peak event, since not every page view converts to a checkout attempt. Zone spread within the region handles a single-zone failure; regional-primary partitioning means, per ADR-003's accepted trade-off, a full regional outage blocks new checkouts for that region's customers until it recovers, with no cross-region write failover.

## 4. Inventory & Order Orchestration Service

**Migration strategy:** Rearchitect (ADR-001) — the one component ADR-002 scoped event-driven adoption to. **Compute:** a separate, dedicated Container Apps environment per region, scaled on Service Bus queue-length rather than HTTP concurrency (ADR-008). **Messaging:** Azure Service Bus, one namespace per region, session-ordered by order ID (ADR-009).

**Hosting architecture.** Unlike the three services above, this one doesn't receive traffic from API Management at all — it has no HTTP ingress. It's triggered entirely by messages on the regional Service Bus namespace's `order-placed` topic. The saga it runs (reserve inventory → confirm payment → create order → hand off to fulfillment) tracks its own in-progress state in a dedicated schema inside that region's Regional Transactional Store (ADR-006, ADR-008's Proposed Configuration) — not a separate database, the same regional-primary PostgreSQL server Cart and Checkout data live in, so orchestration state and the order data it's orchestrating never cross a regional boundary independently of each other.

**Public or private:** entirely private — no public ingress of any kind. It reads from Service Bus, writes to PostgreSQL, and publishes downstream events (`inventory-reserved`, `payment-confirmed`, `order-confirmed`) back onto the same regional Service Bus namespace, which Fulfillment/Warehouse (an existing, out-of-scope system per `problem-statement.md` §5) subscribes to.

**Scaling and HA.** KEDA's Service Bus queue-length scaler targets roughly 15 messages per replica, from a 2-replica regional floor to roughly 25 replicas during a named peak event (ADR-008's Proposed Configuration). A failed saga step (for example, inventory reservation fails because stock ran out between page load and checkout) is handled by the saga's own compensation logic, not by Service Bus retry alone — the service explicitly releases whatever it already reserved before surfacing the failure back to Checkout & Payment. A message that fails processing repeatedly (a malformed event, a downstream dependency down) hits Service Bus's dead-letter queue after 10 delivery attempts and fires an on-call alert, instead of silently blocking the queue behind it.

## 5. Global Catalog — shared data tier

Covered in detail in ADR-007; noted here because both Storefront & Catalog (Section 1) and, indirectly, merchandising/back-office tooling (out of scope for this case study, but the write source named in ADR-007) depend on it. One PostgreSQL primary in the US region accepts all catalog writes; EU and APAC each read from their own asynchronously-replicated, read-only copy — never from the US primary directly, and never from each other. Azure Cache for Redis in each region sits in front of that region's replica as a read-through accelerator, not a second source of truth. This is the one piece of the data tier that crosses regions in steady-state operation; every other data path (Cart, Checkout, Orders, Order Orchestration's saga state) stays entirely within its own region, per ADR-003.

## 6. Summary — public exposure and identity per service

| Service | Public entry point | Identity | Private data path |
| --- | --- | --- | --- |
| Storefront & Catalog | Azure Front Door → regional API Management | None required to browse; Entra External ID token only for signed-in personalization | Regional API Management → Container Apps → Redis (cache) → PostgreSQL replica (private endpoint) |
| Cart | Azure Front Door → regional API Management | Entra External ID token (session-scoped) | Regional API Management → Container Apps → Redis (session state) → PostgreSQL primary (write-behind) |
| Checkout & Payment | Azure Front Door → regional API Management (own subnet, own NSG) | Entra External ID token | Regional API Management → Container Apps (`snet-checkout`) → PostgreSQL primary (private endpoint); raw card data never enters this path at all (ADR-004) |
| Inventory & Order Orchestration | None — Service Bus-triggered only | N/A — no user-facing identity, service-to-service via managed identity | Service Bus → Container Apps → PostgreSQL primary (saga state) → Service Bus (downstream events) |

No owned service in this design has a database, cache, or compute tier reachable directly from the public internet — every public entry point is Azure Front Door, terminating public traffic and continuing over a private path from there, the same closing statement Case Study 3's equivalent document made and the same property this design was built to preserve.
