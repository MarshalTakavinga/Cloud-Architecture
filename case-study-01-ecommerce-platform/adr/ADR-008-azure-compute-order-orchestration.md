### ADR-008: Azure compute for Inventory & Order Orchestration

**Context:**
ADR-001 decided Inventory & Order Orchestration is Rearchitect  event-driven, asynchronous, replayable, the one place ADR-002 scoped event-driven adoption to. It's a different shape from Storefront & Catalog, Cart, and Checkout & Payment (ADR-005): those are synchronous, request/response, and reachable from the API Gateway. Order Orchestration reacts to events on the Event Bus (ADR-009)  order placed, inventory reserved, payment confirmed  rather than serving inbound HTTP traffic directly, so its compute question is genuinely separate and gets its own ADR rather than being folded into ADR-005.

**Options considered:**
- Run Order Orchestration in the same Azure Container Apps environment as Storefront & Catalog/Cart (ADR-005), just with a different scaling trigger (queue-length instead of HTTP-concurrency).
- Azure Functions, Premium plan, event-triggered off the Event Bus.
- A dedicated Azure Container Apps environment for Order Orchestration, scaled on Service Bus queue-length via KEDA.

**Decision:**
A dedicated Azure Container Apps environment per active region, hosting the Order Orchestration service, scaled via KEDA's Service Bus queue-length scaler rather than HTTP concurrency.

**Rationale:**
Sharing the Storefront & Catalog/Cart environment is rejected for the same structural reason ADR-005 gave Checkout & Payment its own environment: Order Orchestration's load pattern is fundamentally different from browse/cart traffic  it's driven by order volume and Service Bus backlog depth, not HTTP request concurrency  and mixing scaling triggers inside one environment makes capacity planning and incident diagnosis harder for no real benefit, since the two don't share meaningful resource pressure in the first place. Azure Functions was seriously considered  it's a natural fit for discrete, event-triggered work, and Case Study 3 used it for exactly this shape of problem (LinkEngine's subscriber logic, ADR-008 there). It's rejected here specifically because Order Orchestration isn't a single-hop reaction to one event the way a LinkEngine subscriber is  it's a multi-step saga (reserve inventory → confirm payment → create order → hand off to fulfillment) that needs to track its own in-progress state across several asynchronous steps, retry individual steps, and compensate (release a reservation) if a later step fails. That's a workflow-orchestration shape, not a stateless function-per-event shape, and forcing it into individual Function invocations would mean re-inventing saga-state tracking on top of a platform that isn't built to hold it, rather than writing that logic once inside a long-running service process that owns its own retry/compensation logic directly. A dedicated Container Apps environment keeps the same operational model ADR-005 already established (no cluster to operate) while giving KEDA a queue-length trigger instead of an HTTP trigger  the same underlying scaling engine, pointed at the signal that actually matters for this component.

**Trade-off:**
A third Container Apps environment per active region (nine total across the three regions, alongside the two from ADR-005) adds more platform surface to monitor and more minimum-overhead cost than consolidating would. Accepted for the same reason ADR-005 accepted it for Checkout & Payment: clean separation of scaling behavior and blast radius is worth more here than the marginal savings of consolidation, particularly because Order Orchestration failures (a stuck saga, a backlog of unprocessed orders) are exactly the kind of incident that's easier to diagnose when its compute isn't also carrying Storefront & Catalog's browse traffic. Queue-length-based scaling also means Order Orchestration's replica count can lag a true event burst by one KEDA polling interval (default 30 seconds)  accepted because order placement itself isn't latency-critical the way a product-page load is; a few seconds of processing lag on a backlog is materially less costly than under-provisioning the customer-facing browse and checkout tiers.

Two gaps this ADR names but doesn't close. First: co-locating saga state in the same regional PostgreSQL primary as Cart, Checkout, and Order data (the choice made below) means the orchestration service's own read/write load  reservation writes, compensation writes, retry-driven re-reads  competes for that instance's connections and I/O with the transactional traffic it's coordinating, and that competition peaks at exactly the moment both workloads peak together. ADR-006's peak-event compute sizing (Standard_D16ds_v5) was not derived against this combined load; it was sized against Cart/Checkout/Order traffic alone. That sizing should be revisited once real saga-state write volume is known (Step 12), not assumed to already have headroom for it.

Second: this ADR's Scaling and HA behavior, and `application-architecture.md` §4, cover a single failed saga step (for example, a stock-out during inventory reservation) and a malformed message reaching the dead-letter queue  both handled by the saga's own compensation logic or Service Bus's retry/dead-letter mechanics. Neither covers a saga caught mid-flight  inventory already reserved, payment not yet confirmed  when its entire region becomes unreachable. ADR-003's accepted trade-off (no cross-region failover; a customer loses write availability for an in-flight cart/order until the region recovers) covers the data-availability consequence, but not the orchestration-specific one: a reservation held against real inventory with no compensating release until that region recovers. This is accepted here on the same basis ADR-003 accepted the broader regional-outage trade-off, but is named explicitly as an open risk rather than resolved  an extended regional outage may need its own mitigation (for example, a reservation TTL with automatic release) if this case study is extended further.

**Proposed Configuration:**

| Setting | Value |
| --- | --- |
| Compute | Azure Container Apps, dedicated environment per active region |
| Workload profile | Consumption + Dedicated (D2 general-purpose) mixed profile |
| Baseline replicas (floor) | 2/region |
| Peak replicas (ceiling, 25x event) | ~25/region |
| Scale rule | KEDA `azure-servicebus` scaler, target ~15 messages per replica on the `order-placed` queue, evaluated every 30 seconds |
| Saga-state store | Azure Database for PostgreSQL Flexible Server, same regional instance as ADR-006 (a dedicated schema/table set for in-flight saga state, not a separate database)  keeps orchestration state in the same regional-primary boundary as the order data it's orchestrating |

**Status:** Approved
