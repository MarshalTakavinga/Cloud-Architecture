### ADR-002: Target architecture style for the components Solstice owns

**Context:**
ADR-001 decided *how* each component moves. This ADR decides *what pattern the system evolves toward*  a separate question, kept separate on purpose (see `architecture-options-and-styles.md` §1). The system has to satisfy three distinct pressures at once: survive a 20–25x elastic traffic multiplier without repeating the November 2024 outage (`requirements.md` §3), serve three continents at acceptable latency while keeping EU customer data resident in the EU (`requirements.md` §3), and shrink PCI-DSS scope around one specific data flow (`current-state.md` §3)  without over-building for problems Solstice doesn't have.

**Options considered:**
- Full microservices decomposition (service-per-feature) vs. a small number of independently-scalable, bounded services
- Event-driven architecture applied platform-wide (full CQRS/event sourcing) vs. scoped to the one component whose problem it actually solves
- Multi-region active-active everywhere vs. active-active for reads only, with regional-primary writes
- A platform-wide Zero-Trust-style compliance overlay vs. a narrowly-scoped PCI isolation boundary around Checkout & Payment only

**Decision:**
A small number of independently-scalable services (not full microservices); event-driven orchestration scoped to the Inventory & Order Orchestration write path only (not platform-wide CQRS/event sourcing); multi-region active-active for the Storefront & Catalog read path, with regional-primary writes for Cart, Checkout & Payment, and Orders; and a narrowly-scoped PCI isolation boundary around Checkout & Payment only, built on the payment gateway's existing hosted-tokenization capability.

**Rationale:**
Full microservices would trade the current monolith's coupling problem for a distributed-systems-operations problem Solstice's 22-person engineering org isn't staffed to run well  the same restraint Case Study 3 applied for a smaller team, arrived at independently because the underlying trade-off (operational surface area vs. team size) doesn't change with team size, only the specific ceiling does. Applying event-driven patterns platform-wide would introduce eventual consistency and replay/ordering complexity into components  Cart, Checkout  that are inherently synchronous and don't have the problem event-driven design solves; scoping it to Inventory & Order Orchestration, the one component with an actual tightly-coupled synchronous chain, targets the fix at the real problem instead of applying a fashionable pattern everywhere. Multi-region active-active for reads directly answers the EU/APAC latency requirement  a customer's product-page and search requests are served from the nearest live region, not a single US region, which is the entire mechanism behind closing the ~2.1s-to-≤150ms latency gap named in `requirements.md`. Regional-primary writes for Cart/Checkout/Orders is what actually satisfies the GDPR data-residency requirement structurally: an EU customer's cart and order records are written and stored in an EU region as the primary copy, not replicated there after the fact from a US master. A platform-wide Zero-Trust-style overlay, modeled on Case Study 3's ADR-002, was considered and rejected here specifically: that overlay exists because Case Study 3's forcing event was a credential-compromise incident affecting the whole application's trust posture, while Solstice's forcing event (the PCI-DSS finding) is about one specific data flow  cardholder data transiting the general application tier. Building a platform-wide compliance boundary to fix a one-flow problem would be over-engineering relative to the actual finding.

**Trade-off:**
Regional-primary writes mean Cart, Checkout, and Order data is not globally replicated the way the Storefront & Catalog read path is  a customer whose region fails over loses write availability for their in-flight cart/order until that region recovers, a real availability trade-off accepted deliberately in exchange for satisfying data residency structurally rather than through a compensating control. Scoping event-driven adoption narrowly means the team carries two different operating models side by side (synchronous services for Cart/Checkout, asynchronous event-driven for Order Orchestration) rather than one consistent pattern everywhere  a real cognitive-overhead cost, accepted because applying one pattern uniformly would mean either over-engineering the synchronous components or under-solving the orchestration component's actual problem.

**Status:** Approved
